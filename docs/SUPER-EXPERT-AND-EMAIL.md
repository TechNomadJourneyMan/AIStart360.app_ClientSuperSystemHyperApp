# SuperExpert и транзакционные письма

Дата: 2026-09-20. Ветка: `claude/aistart360-invites-gri-superexpert-f1134d`.

Документ описывает три связанных блока: почтовую систему (Resend), роль
`SuperExpert` с отдельным кабинетом и приглашения с ролью.

---

## 1. Почтовый слой — `lib/email/`

| Файл | Зачем |
| --- | --- |
| `brand.ts` | фирменные цвета (из логотипа), отправитель, поддержка, часовой пояс, формат даты/времени |
| `layout.ts` | единый макет письма: таблицы + inline-CSS, адаптив, экранирование, запасная ссылка |
| `templates.ts` | тексты и данные писем (приглашение, анкета, GRI, доступ) |
| `send.ts` | отправка в Resend: идемпотентность, журнал доставки, повтор при временной ошибке |
| `notify.ts` | событийный слой — то, что вызывает бизнес-код |
| `notification.ts` | старый API (`sendNotificationEmail`, `sendUserEmail`), переведён на общий макет |

Точка входа одна: `import { ... } from '@/lib/email'`.

### События → письма

| Событие платформы | Функция | Где вызывается | Ключ идемпотентности |
| --- | --- | --- | --- |
| InvitationCreated | `sendPortalInvitationEmail` | `lib/admin/invites.ts` | нет (пересылка разрешена, ограничена rate-limit) |
| QuestionnaireCompleted | `sendQuestionnaireCompletedEmail` | `app/api/v1/onboarding/survey/route.ts` | `questionnaire_completed:<userId>` |
| GRICompleted | `sendGriCompletedEmail` | `app/api/v1/gri/assessment/route.ts` | `gri_completed:<assessmentId>` |
| PortalAccessGranted | `sendPortalAccessGrantedEmail` | `lib/users/approval.ts` | нет (решение можно повторить) |

### Что в письме

Общий макет: логотипный блок, заголовок, приветствие, абзацы, таблица фактов
(компания, роль, статус, дата, время с поясом), цитата (сообщение от
пригласившего), CTA-кнопка, запасная ссылка текстом, подвал с поддержкой и
копирайтом. Пустые необязательные поля не рисуются вовсе.

Безопасность: любое значение экранируется (`escapeHtml`), CTA принимает только
`http(s)` (`safeUrl`). В логи не попадают ни ссылки (в них одноразовые токены),
ни тело письма — только вид письма, адрес и статус.

### Переменные окружения

```
RESEND_API_KEY=       # обязательна, иначе письмо честно не уходит
EMAIL_FROM=           # отправитель; домен должен быть верифицирован в Resend
EMAIL_REPLY_TO=       # адрес для ответов (необязательно)
SUPPORT_EMAIL=        # адрес в подвале письма
EMAIL_TIMEZONE=       # пояс даты/времени, по умолчанию Asia/Almaty
AUTH_URL=             # база для ссылок (см. lib/site-url.ts)
```

## 2. Роль SuperExpert

Роль живёт в существующей системе RBAC (`lib/admin/rbac.ts`, таблица
`staff_roles`) — это не алиас администратора и не вторая система прав.

¹ Вход в кабинет клиента для SuperExpert выключается тумблером
`super_expert_impersonation` в настройках платформы (по умолчанию включён).
Проверка на сервере, в маршруте импersonation. Кабинет сотрудника не
открывается никому — `canImpersonate` отказывает для любой staff-цели.

Новые права: `users.invite` (приглашения), `users.approve` (решение по заявке)
и `company.edit` (данные компании клиента)
выделены из `users.manage`, чтобы SuperExpert мог работать с людьми, не получая
тарифы, блокировки, 2FA и чтение системных настроек.

Право `clients.review` (2026-09-24, пакет 1a) — всё, что эксперт *пишет
клиенту*: корректировка Точки Б, публичный комментарий к блоку кабинета,
статус / приоритет / рекомендация по обращению (`expert_cases`). Читать эти
вкладки может любой, у кого есть `users.view` + `users.sensitive`.

### Область видимости клиентов (scoping)

`staff_roles.client_scope` (миграция 086): `'all'` — сотрудник видит всех
клиентов (по умолчанию), `'assigned'` — только тех, где он ответственный
(`user_assignments.assignee_id`, вкладка «Задачи» → «Ответственный»).
SuperAdmin, Admin и CRM-менеджер всегда видят всех (`effectiveClientScope`).

- `GigaActor.clientScope` читается в `staffRoleOf` на каждом запросе.
- `lib/admin/client-scope.ts`: `assignedClientIds`, `scopedClientIds`,
  `canAccessClient`, `guardClientAccess` — последний вызывается сразу после
  `requireGiga` в каждом `app/api/giga-admin/users/[id]/*` и отвечает 403
  «Клиент вам не назначен» (400 на не-UUID).
- Списки фильтруются по назначенным: пользователи (+ выгрузка, массовые
  напоминания), аккаунты, анкеты (лента правок, поиск по ответам, превью),
  GRI, активность, CJM, дубликаты, задачи, «Мой день».
- Переключатель в интерфейсе делает модуль «Эксперты» (отдельная задача);
  до него — `UPDATE staff_roles SET client_scope='assigned' WHERE user_id=…`.

Ранг роли — 60 (между Admin 80 и CRM-менеджером 50): SuperExpert не может
действовать на равных или старших сотрудников и не может выдавать роли вообще
(`grantableRoles('super_expert') === []`).

### Где проверяются права

Каждый маршрут `/api/giga-admin/*` вызывает `requireGiga(req, permission)` —
проверка на сервере, до обращения к данным. Интерфейс только прячет то, что и
так запрещено. Тест `tests/unit/giga-crm/super-expert.test.ts` бьёт по реальным
маршрутам и убеждается, что 403 приходит раньше, чем маршрут коснётся базы.

## 3. Кабинет SuperExpert

- Вход: `/super-expert/login` (та же аутентификация Supabase, после входа
  сервер подтверждает права; иначе сессия закрывается и показывается отказ).
- Кабинет: `/super-expert` — «Мой день», главная, пользователи, заявки,
  аккаунты, анкеты, GRI, активность, приглашения.
- «Мой день» (`/super-expert/today`, в GIGA-CRM — `/admin-giga-panel/today`,
  API `GET /api/giga-admin/me/today`): мои открытые задачи (просрочено /
  сегодня / 7 дней), открытые обращения по приоритету (все или только по моим
  клиентам — по scope) и «Что изменилось» — клиенты, у которых после моего
  последнего открытия карточки изменились анкета, GRI, Точка А или документы.
  Сводка детерминированная, без LLM: «Анкета: 3 ответа изменены · GRI: новый
  замер 6.1 (+0.4)». Момент просмотра пишет `GET users/:id/profile` в
  `staff_client_views` (миграция 086).
- Карточка пользователя: `/super-expert/users/<id>` (профиль, анкета,
  **Точка А, Точка Б**, GRI, **Пульс, Кейсы, Комментарии**, активность, CJM,
  документы, заметки, задачи, письма, качество данных, история).

### Экспертные вкладки User 360 (перенесены из портала `/expert`)

| Вкладка | API | Источник данных |
| --- | --- | --- |
| Точка А | `GET users/:id/point-a` | `diagnostics` (текущая + история), текущий `gri_assessments` |
| Точка Б | `GET/POST users/:id/point-b` | расчёт `calculatePointBV2` + `point_b_versions` |
| Пульс | `GET users/:id/pulse` | `gri_pulse_responses`, явные `ai_analysis.pulse` |
| Кейсы | `GET/PATCH users/:id/cases` | `expert_cases` (статус, приоритет, рекомендация; аудит) |
| Комментарии | `GET/POST users/:id/comments`, `DELETE .../:commentId` | `expert_comments` (публичные, клиент получает уведомление) |

Данные честные: никаких `DEFAULT_SCORES`, «риска = 100 − балл» и даты
диагностики вместо «последнего заказа» — нет данных, значит пустое состояние.
Запись (Точка Б, комментарий) — только для аккаунтов-клиентов (`role='client'`
без строки в `staff_roles`).

### Старый портал эксперта выведен

`app/(expert)/expert/*` теперь только перенаправляет в `/super-expert`
(`/expert/clients/<id>` → карточка User 360); `app/api/expert/**`,
`components/expert/**` удалены. Клиент читает комментарии экспертов через
`GET /api/v1/expert-comments` (только свои). Middleware: пользователь с
`profiles.role` `expert` / `manager` / `analyst` без роли в `staff_roles`
попадает на `/super-expert/login?denied=1`, с ролью — в свой кабинет.

Экраны общие с GIGA-CRM: реализация лежит в `components/giga-panel/pages/`, а
базовый путь, меню и подпись приходят из `WorkspaceContext`. Поэтому одна
правка чинит оба кабинета, а ссылки внутри кабинета SuperExpert никогда не
уводят в админскую панель.

Шлагбаум в `middleware.ts`: без сессии — на `/super-expert/login`; с сессией, но
без подходящей роли персонала — туда же с `?denied=1`; 2FA-требования такие же,
как у ГИГА-Панели.

## 4. Приглашения

- `platform_invitations` (миграция 081) — запись о приглашении: кому, кем, с
  какой ролью, до какого времени действует, чем закончилось. **Токен не
  хранится**: одноразовую ссылку выдаёт Supabase, живёт она только в письме.
- Приглашение с ролью — это выдача прав, поэтому его может создать только
  сотрудник с правом `roles.manage` и только ролью не выше своей.
- Принятие: `/auth/verify` → `acceptInvitation()` закрывает запись, выдаёт роль
  и переводит профиль в «одобрен». Повторно ту же запись закрыть нельзя,
  просроченная ссылка роли не даёт.

### Первое приглашение из терминала

```bash
npx tsx scripts/invite-staff.ts --email=user@example.com --role=super_expert --dry-run
```

Без `--dry-run` письмо уходит по-настоящему. `--grant-now` выдаёт роль сразу,
не дожидаясь перехода по ссылке (для уже существующего аккаунта).

## 5b. Инструменты работы с клиентом

| Функция | Где | Маршрут |
| --- | --- | --- |
| Напомнить про анкету | карточка + список (массово) | `POST users/:id/remind-survey`, `POST users/bulk-remind` |
| Где застрял | колонка в списке | `admin_list_users` → `survey_filled_steps` |
| Письма клиенту | вкладка «Письма» | `GET users/:id/emails` |
| Заметки | вкладка «Заметки» | `GET/POST users/:id/notes`, `PATCH/DELETE .../:noteId` |
| Ответственный и задачи | вкладка «Задачи» | `GET/PUT users/:id/assignment`, `GET/POST users/:id/tasks`, `PATCH tasks/:taskId` |
| Качество данных | вкладка «Качество данных» | `GET users/:id/quality` |
| Динамика GRI и бенчмарк | вкладка «GRI» | `GET gri/benchmark` |
| Поиск по ответам | раздел «Анкеты» | `GET surveys/search?q=&key=&min=&max=` |
| Выгрузка | список | `GET users/export` (CSV с BOM, разделитель `;`) |
| Дубликаты | раздел «Дубликаты» | `GET duplicates` |

Данные для этого дала миграция 082: `user_notes`, `user_assignments`,
`staff_tasks`, а `admin_survey_steps`/`admin_list_users` научились отдавать
номера заполненных шагов, а не только их количество.

«Стадия бизнеса» из интерфейса персонала убрана: поле дублировало отрасль и
размер, решения по нему никто не принимал. Колонка `companies.stage` в базе
осталась — её читают расчёты Точки А, и они корректно работают с пустым
значением.

## 6. Автоматическая проверка кабинета

```bash
npx tsx scripts/qa-super-expert.ts --base=http://localhost:3000
```

Заводит служебный аккаунт, выдаёт ему `super_expert`, получает настоящую сессию
по одноразовой ссылке (пароль не нужен) и прогоняет 59 проверок: страницы
кабинета, разрешённые данные, тринадцать запрещённых маршрутов и отзыв роли.
В конце роль снимается, чтобы не оставалось лишнего привилегированного
аккаунта; `--keep` оставляет её для ручных проверок.

Почему через API, а не кликами: клик по спрятанной кнопке ничего не
доказывает — прямой запрос к запрещённому маршруту доказывает.

Письма проверяются отдельно:

```bash
npx tsx scripts/send-test-emails.ts --to=<один адрес>
```

**Грабли:** не создавайте временные файлы в корне проекта, пока запущен
`next dev` — watcher ловит их, Fast Refresh перемонтирует страницу, и это
выглядит как самопроизвольные переходы по разделам.

## 7. Ручная проверка

1. Открыть `/super-expert/login`, войти приглашённым аккаунтом.
2. Перейти в «Пользователи», открыть карточку.
3. Проверить вкладки «Анкета» и «GRI».
4. Отправить приглашение из раздела «Приглашения».
5. Убедиться, что в меню нет «Настройки», «Роли», «Журнал аудита»,
   «Вход от имени», «Контент».
6. Запросить запрещённое напрямую — доступ должен быть закрыт сервером:

```bash
curl -i -b "<cookies сессии>" https://portal.aistart360.app/api/giga-admin/settings
# ожидаемо: 403 {"ok":false,"error":"Недостаточно прав","missing":["users.manage"]}
```
