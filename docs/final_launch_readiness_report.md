## 4. Что было исправлено (Critical / High)

### Critical
- **Эскалация привилегий через саморегистрацию `role='owner'`.** `lib/rbac.ts` маппил `owner → SUPER_ADMIN`, а `getAdminSession` не проверял статус одобрения — самозарегистрированный «член команды» получал полный доступ к `/api/admin/*`. Исправлено: `owner` больше не привилегированная роль (у неё своя зона `/owner/*`, и `supabase-admin-guard` её не пускает); добавлена проверка `profiles.status` (не-approved аккаунты не получают повышенных прав).

### High
- **IDOR:** `/api/v1/me`, `point-a`, `metrics`, `profile` определяли личность из подделываемой httpOnly-куки `aistart360_user_id` **раньше** сессии → любой залогиненный пользователь мог читать чужие данные. Введён `lib/current-user.getSessionUserId` (только Supabase-сессия); кука-идентификатор убрана отовсюду, где была авторитетной.
- **Неаутентифицированный `/api/pulse` (+ `/briefing`):** роль бралась из неподписанной куки с дефолтом `expert` → аноним мог читать все CRM-сделки и жечь бюджет OpenRouter. Переведено на Supabase-сессию + роль из БД; briefing ограничен staff-ролями и rate-limit.
- **Утечка данных через service worker:** дефолтный `@ducanh2912/next-pwa` NetworkFirst-кэшировал все `GET /api/*` на 24ч, кэш не чистился при logout → на общем устройстве следующий пользователь получал данные предыдущего. Исправлено: `/api/*` → `NetworkOnly`; logout чистит react-query-persist + CacheStorage.
- **Мёртвый NextAuth ломал CRM-интеграции** (Settings → Интеграции всегда 401). Переведено на Supabase-сессию (`lib/crm/auth`): корректный 401 для анонима, обработанный 403 «нет организации» для юзеров.
- **23.5 МБ мёртвых медиа в precache** сервис-воркера — удалены (`public/gri-pulse-*`), добавлен `publicExcludes`.
- **middleware гонял сетевую авторизацию для статики** (`.ttf/.m4a/.css/.js`) и редиректил анонимов на `/login`, ломая SW-precache — статика теперь минует auth.
- **owner/expert без мобильной навигации** — добавлен бургер + drawer в их хедеры.
- **Кнопка «Выход» в comnate ожидания / загрузке документов** не завершала Supabase-сессию → pending-клиент зацикливался. Исправлено.
- **Дублирующиеся тосты** (4 экземпляра `<Toaster>`) → один глобальный.
- **Переключатель темы** обещал светлую/системную, но менял только класс без эффекта → честное состояние (тёмная активна, остальные «скоро»).

Тесты после Critical/High: typecheck 0 ошибок, 551 passed / 11 skipped, build OK.

## 5. Что улучшено в UI/UX

- **Брендовый 404** (`app/not-found.tsx`): тёмный фон, teal-градиент «404», русский текст, логотип, кнопки — вместо белого английского дефолта Next.
- **Брендовый прелоадер** (`components/ui/Preloader.tsx`): 3 концентрических кольца разной скорости + пульсирующий логотип, в стиле лендинга, на портальных токенах; `prefers-reduced-motion`. Корневой `app/loading.tsx` использует его.
- **Синхронизация навигации с middleware:** из клиентского сайдбара убраны 5 пунктов, которые молча редиректили на `/dashboard`; удалён несуществующий `/market/monitoring` (404).
- **Русификация** заголовков вкладок и H1 (Settings/Reports/Analytics/Clients/Team/Intelligence/admin) — были английскими в русском UI.
- **Error-страницы** приведены к бренду; исправлена иконка-слово `material-symbols-rounded`; `global-error` сделан самодостаточным (inline-стили).
- **Скелетоны** во всех 25 `loading.tsx` переведены с серо-синих tailwind-дефолтов на токены темы (убран «чужой» flash).
- **FAB «Ассистент» больше не перекрывает** контент (нижний отступ layout — заодно закрыл перекрытие мобильным баром).
- **Доступность:** глобальный `prefers-reduced-motion`; aria-label на колокольчиках/бургерах; focus-friendly drawer'ы.

## 6. Что улучшено в performance

- **Service worker** больше не кэширует приватные API и не тянет 23.5 МБ мёртвых медиа в precache (манифест SW: было ~208 записей с .m4a → стало ~198 без них).
- **middleware** не выполняет 2 сетевых вызова (getUser + profiles) на каждый статический файл.
- **Header-часы** вынесены в изолированный `<HeaderClock/>` — 1-секундный тик больше не ре-рендерит весь 380-строчный Header на всех страницах dashboard-группы.
- Подтверждено, что перф-фиксы прошлого аудита (таймауты AI, recharts→dynamic на 6 поверхностях, rate-limit, FK-индексы в схеме, пагинация) на месте.

**Замеры (production build, First-Load JS):** /pulse 111 kB, /settings 109 kB, /point-a 282 kB, /metrics 291 kB, /dashboard ~300 kB, /gri 344 kB. Крупные — это большие `'use client'` модули (документированный долг F02, разбиение — следующая итерация). Транзитивно (gzip) это ~90–170 kB; при нормальной сети ключевые страницы укладываются в <5 c.

## 10. Известные ограничения (не блокеры запуска)

- **Светлая тема** отсутствует (все токены — абсолютно тёмные, нет `dark:`-вариантов). Честно помечена «скоро».
- **Эквайринг** — намеренная демо-заглушка.
- **CRM-интеграции** (Bitrix24/amoCRM) архитектурно осиротели: модель Prisma-org-scoped, у Supabase-пользователей нет моста к Prisma-организации → фича возвращает честный 403 «нет организации». Требует моста Supabase→org или переезда модели.
- **`GrowthSnapshotHero`** (виджет «Снимок Точки А») на части заходов показывает пустое состояние, хотя цели заданы — клиентская логика/тайминг фетча этого виджета (пред-существующее, не регрессия; см. предложение DG-4).
- **Крупные `'use client'` страницы** (pulse/metrics и др.) не разбиты — First-Load JS остаётся большим.
- **owner/expert-мобильная навигация** добавлена как drawer в хедере; полноценная адаптация их layout'ов (`hidden lg:flex` сайдбары) — отдельная задача.
- **Prisma-миграции** применяются вручную (`prisma db push`); FK-индексы из schema.prisma **ещё не применены** к прод-Supabase.
- ~5.9 тыс. строк мёртвого кода и ~7 неиспользуемых зависимостей (перечислены в баг-листе) — не влияют на работу, чистить в отдельной итерации.

| Риск | Уровень | Митигация |
|---|---|---|
| FK-индексы не применены к прод-БД | Средний | Выполнить `prisma db push` (или `migrate deploy`) перед нагрузкой — см. §12 |

## 12. Инструкция запуска (локально)

```bash
# 1. Зависимости
npm install                    # postinstall прогонит prisma generate

# 2. Переменные окружения (см. .env.example — это источник истины)
#    Ключевые: NEXT_PUBLIC_SUPABASE_URL, NEXT_PUBLIC_SUPABASE_ANON_KEY,
#    SUPABASE_SERVICE_ROLE_KEY, DATABASE_URL, OPENROUTER_API_KEY,
#    AUTH_SECRET/AUTH_URL, GIGA_ADMIN_PASSWORD
cp .env.example .env.local     # заполнить значениями

# 3. Dev-сервер (важно: запускать ПОСЛЕ создания .env.local — NEXT_PUBLIC_*
#    инлайнятся в бандл на этапе компиляции)
npm run dev                    # http://localhost:3000

# Тестовые аккаунты (seed): client@aistart360.test / expert@... / admin@...  пароль Test1234!
#   node scripts/seed-test-data.js   — если нужно пересоздать
```

## 13. Инструкция финальной проверки перед деплоем

```bash
npm run type-check     # ожидается: 0 ошибок
npm run lint           # ожидается: 0 ошибок
npm test               # ожидается: 551 passed, 11 skipped
npm run build          # ожидается: exit 0, ~103 страницы

# ВАЖНО: не запускать `npm run build` при работающем `npm run dev` —
#        production-сборка перезаписывает .next и роняет dev-сервер
#        (Cannot find module './xxxx.js'). Для dev после build: rm -rf .next && npm run dev
```

Перед продом дополнительно:
1. **Ротировать пароль Supabase** (утечка в git-истории).
2. **Применить схему Prisma** к прод-БД (`prisma db push`) — FK-индексы.
3. Задать `AUTH_URL` в проде (иначе OG/canonical укажут на localhost).
4. Проверить, что service worker переустановился (новая runtimeCaching-стратегия): в DevTools → Application → Service Workers → Update.
5. Ручной проход входа всех ролей (client / expert / owner / admin / super_admin) и PDF-экспорта.

## 14. Рекомендации по дальнейшему развитию

Приоритеты — в `docs/product_ux_improvement_proposal.md` (§11). Ближайшая итерация:

1. **P0/P1 продукт:** визард первого запуска (ON-1), единый источник GRI (DG-1), объяснимость реалистичности цели (DG-3), Action Plan как чек-лист (EN-3), ярлыки происхождения данных (TR-1).
