# Security / Auth / RLS / Data-Integrity Audit — 2026-07-07

**Auditor scope:** auth flows, giga shared-password panel, RBAC/privilege-escalation, IDOR, SSRF, RLS, secrets, security headers/CSP, MFA/WebAuthn, data-model consistency.
**Method:** read the two prior audit docs (`SECURITY-AUDIT-AND-2FA-PLAN-2026-07-02.md`, `AUDIT-admin-panel-2026-07-04.md`), then verified each claim against current code at branch `claude/zen-swirles-7be268` (HEAD `8deeb51`). Line numbers checked at audit time; re-verify before editing.
**ID prefix:** SEC. Severity ∈ Critical/High/Medium/Low.

> This report is read-only. No source was modified.

## Summary

Since the two prior audits the team has closed the large majority of Critical/High items: the giga-panel user-approval path now writes the single source of truth (`profiles.status`) through a service-role helper with an affected-row check (`lib/users/approval.ts`), the privilege-escalation vector in `admin/requests/[id]/approve` is validated and SUPER_ADMIN-gated, 2FA recovery exists (`giga-admin/users/[id]/2fa-reset` + admin MFA wipe), a registration-mode toggle is live, `next` is bumped to a patched `14.2.35`, the SSRF storage-URL guard is applied at both document insert and process, security headers/CSP are strong, the dev registration backdoor is double-gated, and self-registration cannot self-assign staff roles. The remaining exposure is concentrated in three areas: (1) **the giga panel is still a single shared-password super-admin with no individual identity, no MFA, and no working audit trail** — its `logAudit` writes silently fail against an FK to the dead `users` table, so the most privileged surface in the product is effectively unaudited; (2) **Prisma-owned tables (`admin_requests`, `audit_logs`, `comments`) have RLS disabled** on a database whose anon key is a public build-time env, which is exactly what lets the **unauthenticated `POST /api/client/register`** spam `admin_requests`; (3) **a live Supabase DB password remains in git history** and must be rotated. Several medium/low data-integrity and defense-in-depth items from the prior audits are still open (plaintext CRM tokens, fail-open status default in the auth store, "block user" that only clears dead NextAuth sessions, AI insights visible to users with no approval gate, two giga read routes broken by using the anon client).

## Spec notes (security TZ items)

1. **Consolidate the admin surface / retire the shared password (SEC-05).** The prior TZ already recommends binding the giga panel to a real super_admin Supabase session. This is the single highest-leverage security change: it fixes attribution, brings giga under the MFA gate, and lets the audit trail carry a real actor id (unblocking SEC-02).
2. **Lock down Prisma tables (SEC-03).** Decide per table: `admin_requests`/`audit_logs`/`comments` are server-only — `REVOKE` anon/authenticated PostgREST access (simplest, safest) rather than authoring RLS. This also hard-closes SEC-04's anon-REST fallback insert.
3. **Unified, working audit trail (SEC-02).** Either relax the `performedBy` FK to a plain string or move audit to a Supabase table with no FK; every privileged mutation (approve/reject, role change, 2fa-reset, impersonate, block, registration-mode change, insight publish) must produce a persisted, queryable row.
4. **Insight lifecycle (SEC-08).** The prior TZ's `draft→pending_review→approved→published` with a `visible_to_user` gate remains unimplemented; AI output is still user-visible on insert.
5. **Secret encryption rollout (SEC-06).** The crypto foundation is done; apply it to CRM tokens (and any future provider API keys) — the TZ already scoped this.
6. **MFA policy (SEC-05/SEC-11).** Consider mandatory MFA for super_admin/admin and stronger password policy; both were flagged and neither is enforced.
