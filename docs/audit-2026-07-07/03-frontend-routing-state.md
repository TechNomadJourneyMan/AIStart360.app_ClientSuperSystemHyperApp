**Auditor scope:** FE (routing, components, state, forms, error/empty/loading, client/server boundaries).

**Surface:** 81 `page.tsx`, 180 `components/*.tsx` (~42k LOC), 5 Zustand stores, 8 hooks, 5 route groups + `client/`, `admin-giga-panel`, `2fa`, `presentation`, `r/[token]`.

---

## Summary

The routing layer is fundamentally sound: middleware (`middleware.ts`) enforces role-based access with correct whole-segment matching, MFA step-up, and a signed giga-cookie gate, and 46/81 pages are true Server Components — the App Router is *not* being abused with blanket `'use client'`. The two systemic problems are **duplication** and **state-strategy incoherence**. Three conceptual pages (`dashboard`, `gri`, `profile`) exist as three independently-maintained copies each (dashboard/owner/expert), with visible constant drift already present; the `layout/` directory carries 4 parallel Sidebars and 3 parallel Headers; Point-A ships two coexisting generations (v1 + v2); GRI ships three assessment engines. On state: a well-configured, localStorage-persisted React Query cache exists in `providers.tsx` but is used by only ~6 files while ~84 components fetch via raw `fetch`-in-`useEffect`, producing render-then-fetch waterfalls — and the `(expert)`/`(owner)` groups do client-side waterfalls even where the `(dashboard)` twin already fetches server-side. Auth has two sources of truth (Zustand `useAuthStore` for client redirects vs server `supabase.auth.getUser()`), the role vocabulary is split between two incompatible `UserRole` unions, post-login redirect logic is triplicated (login/register/middleware) and already divergent, persisted Zustand UI state (`sidebarCollapsed`) is read during SSR with no hydration guard (mismatch risk), and error boundaries exist in only 2 of 7 route groups. None of these are release-blocking crashes, but together they make the frontend expensive to change safely.

## Spec notes (frontend TZ items)

**State strategy (canonical).**
- **Server-first data.** Default to Server Components fetching data and passing it down (the `(dashboard)/metrics/page.tsx` pattern). Reserve `'use client'` for genuinely interactive leaves.
- **Client data via React Query only.** The persisted RQ client already exists (`app/providers.tsx`); all client-side reads go through typed hooks in `hooks/` (model: `hooks/useMetrics.ts`). Ban new raw `fetch`-in-`useEffect` for GET data. Keep `useEffect` only for subscriptions/imperative effects (e.g. `hooks/useRealtimeSync.ts`).
- **Auth single source of truth.** Server session is authoritative; hydrate the Zustand store from a server-provided initial user (context/prop) rather than an independent client `getUser()`+`profiles` fetch on mount (FE-05). One `roleLandingPath()` helper for all redirects (FE-06).
- **Role vocabulary.** One `UserRole` enum, lowercase runtime values, imported everywhere; delete `MANAGER`/`ANALYST` dead config (FE-01).
- **Persisted UI state hydration.** Any component reading persisted Zustand values during render must gate on a `hasHydrated` flag or use `skipHydration` (FE-07).

**Component refactors (priority order).** (1) Collapse the 3× dashboard/gri/profile per-role copies into role-parameterized shared components; owner/expert pages become thin wrappers (FE-03). (2) One config-driven Sidebar + Header from `lib/navigation.ts` (FE-10). (3) Pick one GRI engine / shared core; remove the vendored shadcn duplicate (FE-09). (4) Finish Point-A v2, delete v1 (FE-15). (5) Consolidate KPI card + radar families, drop `V2`/`V3` (FE-16). (6) Parameterize client vertical variants (medical/ecommerce) by config (FE-12).

**Error / empty / loading conventions.**
- **Loading:** already strong — 28 `loading.tsx` covering all `(dashboard)` segments + group roots. Keep one per segment.
- **Error:** add an `error.tsx` to every route group (currently 2/7). Reuse `(dashboard)/error.tsx`. Add a shared `<ErrorState reset>` and `<EmptyState>` component so client pages stop hand-rolling these (3 client pages have none: `(owner)/owner/profile`, `admin-giga-panel`, `client/point-b`).
- **Empty:** standardize a single `<EmptyState>` (icon + RU copy + CTA); the expert dashboard's "honest empty state" is the intended tone.

**Forms.** Adopt react-hook-form + Zod uniformly. Today only `(auth)/forgot-password`, `auth/reset-password` use it; `login`, `register`, and the 12-step onboarding use raw `useState` with ad-hoc validation (`register` checks password match/length inline). Define Zod schemas per form; the onboarding survey needs a per-step schema + typed answers object + a single form context (FE-11).

## Product-owner questions

1. **Role model:** Is the true set `admin / expert / owner / client / super_admin` (auth store), or does `MANAGER`/`ANALYST` (nav/permissions) still matter for a future org-hierarchy? This decides whether FE-01 deletes those roles or promotes them into the real enum.
2. **Owner vs Expert vs Admin dashboards:** Should these three converge on one shared, role-scoped dashboard (my recommendation), or are they intentionally different products that justify separate code? Governs how aggressively FE-03/FE-10 consolidate.
3. **GRI engines:** Which of the three (GRICalculator / GRIAssessment / MiniGriWizard) is canonical going forward? Needed before FE-09 consolidation.
4. **Vertical variants (medical / ecommerce):** Are these permanent product lines (warranting a config-driven engine) or experiments to retire? Governs FE-12.
5. **i18n:** Is Russian-only permanent, or is multi-language on the roadmap? Determines whether FE-18 (extract copy) is worth doing.
6. **Premium paywall:** The client "unlock premium" flow currently authenticates against the giga-admin password (FE-13). Is there an intended separate entitlement/promo system, or is this a deliberate temporary stub?
