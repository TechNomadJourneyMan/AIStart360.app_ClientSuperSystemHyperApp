# Сервис ИИ-агентов на Railway

Тот же репозиторий и та же сборка разворачиваются вторым сервисом Railway. Что делает процесс,
говорит переменная `PORTAL_ROLE` (`lib/runtime/role.ts`): `web` — только портал, `agents` — только
работа агентов, не задана — всё в одном процессе, как раньше (локальная разработка, тесты и портал
до переключения).

## Что сервис делает и чего не делает

- Выполняет задачи агентов. Портал, поставив задачу в очередь, сразу сообщает о ней сервису:
  `POST /api/internal/agents/kick` по частной сети, с `Authorization: Bearer <CRON_SECRET>`.
- Раз в минуту сам вызывает `GET /api/cron/agents` (встроенный планировщик) — это его единственный
  цикл обслуживания: агенты по расписанию, повторы после сбоя, зависшие задачи и истёкшие
  одобрения, недоставленные события платформы, очередь уведомлений WhatsApp, пересчёты Точки А.
- Отправляет ежедневную сводку агентов (`/api/cron/agents-digest`, 04:00 UTC).

Не делает: не принимает пользователей (публичного домена нет), не обслуживает функции Inngest,
не запускает очередь Workflow и остальные задачи портала по расписанию.

Пока настройка «Агенты по расписанию (24/7)» выключена, обслуживание идёт раз в 15 минут (минуты
00, 15, 30, 45 UTC): остальные вызовы читают только саму настройку и отвечают `quiet_mode`.
Задача, которую портал передал сервису, выполняется сразу в любом режиме.

## Переменные сервиса

| Переменная | Значение |
|---|---|
| `PORTAL_ROLE` | `agents` |
| `PERSISTENT_SERVER` | `1` |
| `CRON_RUNNER_ENABLED` | `1`; без планировщика очередь никто не обслуживает (в логе будет ошибка) |
| `CRON_SECRET` | тот же, что у портала: им подписаны и вызовы портала |
| `PORT`, `NEXT_MANUAL_SIG_HANDLE` | как у портала (`8080`, `true`) |
| всё остальное | ссылками на переменные портала (`${{<сервис портала>.ИМЯ}}`): база, Supabase, ключи моделей и Inngest, Telegram, WhatsApp, `WORKFLOW_POSTGRES_URL` |

- Публичный домен не создавать: портал обращается к сервису по имени `<сервис>.railway.internal`.
- Команда pre-deploy не нужна. `railway.json` у сервисов общий, но `scripts/railway/predeploy.mjs`
  при `PORTAL_ROLE=agents` завершается, ничего не делая.
- `AGENTS_SERVICE_URL` сервису не нужен: он задаётся только порталу.
- Одна реплика, как у портала. У сервиса свой пул соединений с базой (`PRISMA_CONNECTION_LIMIT`).
- Сервис собирается из той же ветки, поэтому каждый пуш разворачивает оба сервиса.

## Порядок переключения

1. Выкатить код на портал. Без `PORTAL_ROLE` он работает как раньше.
2. Создать сервис из того же репозитория, задать переменные, дождаться запуска. В его логе:
   `server: PORTAL_ROLE=agents - очередь Workflow здесь не запускается…`, `cron: scheduler started`
   и каждую минуту `cron: GET /api/cron/agents -> 200`. Пока портал ещё без роли, одну очередь
   разбирают оба сервиса — это безопасно: задачу захватывает только один исполнитель.
3. Проверить связь из контейнера портала (`railway ssh`), ответ должен быть `200`:
   `node -e "fetch('http://<сервис>.railway.internal:8080/api/healthz').then(r=>console.log(r.status))"`
4. Только теперь задать порталу `PORTAL_ROLE=web` и
   `AGENTS_SERVICE_URL=http://<сервис>.railway.internal:8080` (порт — `PORT` сервиса) и дождаться
   его передеплоя.
5. Пересинхронизировать Inngest: `curl -X PUT https://<домен портала>/api/inngest`. До этого
   Inngest продолжает вызывать у портала функции агентов, которых там уже нет.
6. Поставить задачу (например, загрузить документ) и убедиться, что она выполнена, а в логе
   портала нет строк `[agents] kick failed` и `AGENTS_SERVICE_URL не задан`.

## Откат

1. Убрать у портала `PORTAL_ROLE` и `AGENTS_SERVICE_URL`, дождаться передеплоя.
2. Пересинхронизировать Inngest (`PUT /api/inngest`).
3. Остановить сервис агентов — не раньше первых двух шагов, иначе задачи останутся ждать.

## Предупреждения

- `PORTAL_ROLE=web` без работающего сервиса агентов оставляет задачи ждать в очереди: портал не
  выполняет их ни сам, ни через Inngest. Они выполнятся, когда сервис поднимется.
- Если передача задачи не удалась (`[agents] kick failed: <код>`), задача ждёт ближайшего
  обслуживания: до минуты при включённых «Агентах по расписанию (24/7)», до 15 минут при
  выключенных.
- `401` в этой строке — у сервисов разный `CRON_SECRET`. `ECONNREFUSED` при живом сервисе —
  частная сеть окружения только IPv6 (окружения Railway, созданные до 16.10.2025), а
  `next start -H 0.0.0.0` слушает IPv4.
- Деплой сервиса ждёт идущие задачи до 55 с. Оборванная задача вернётся в очередь, когда истечёт
  её аренда; попытка при этом засчитывается.
