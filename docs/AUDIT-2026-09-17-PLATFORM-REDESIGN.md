## 3. Что остаётся

### Анкета
1. Нет серверного автосейва: несохранённые правки живут только в браузере до «Далее».
2. Маршрут записи без zod, без rate-limit; `company_id` из тела без проверки владельца.
3. Нет retry при сетевой ошибке, нет `beforeunload`-защиты, нет финального подтверждения.
4. Прогресс = позиция (макс. 92%), а не заполненность.
5. Названия табов не совпадают с формами (шаги 5, 7, 9, 12); три разных таблицы названий шагов.
6. E-commerce/medical-ветки пишут в ту же таблицу со своими `step`.

### Точка А / GRI
7. После анкеты → `/client/dashboard` → redirect `/client/point-a` (отдельная клиентская реализация, 600+ строк).
8. GRI: прогресс только в `localStorage` (ключ не per-user, внутри PII); POST один раз после 7 блоков; повторный заход → дубль строки; re-seed подставляет средний балл как ответ на критерий; расчёт дублирован клиент/сервер; «62 критерия» в UI при 67 фактических.
9. `GRIAssessment` не принимает props и не зависит от роутера → встраивается. Мешают только полностраничный `Shell` и тип `AssessmentCurrent` внутри `GriPageShell`.

### GIGA
10. Нет разделов GRI, Активность, CJM, Аналитика; Контент = только модерация инсайтов; Платформа = 4 тумблера.
11. `GET /api/giga-admin/users` — вся БД одним ответом без пагинации.
12. Нет смены роли, архивации, инвайтов; `lastLogin: null`.
13. Дубли: 3 бэкенда одобрения, 2 блокировки, Prisma- и Supabase-справочники, `(dashboard)/users` — мок на localStorage.

### Безопасность (закрыть по ходу)
14. MFA step-up пропускается на `/admin-giga-panel` (ранний `return` в `middleware.ts`).
15. Impersonate: любой target (включая super_admin), без причины, без rate-limit; вызывает admin API anon-клиентом.
16. IDOR: любой `expert` читает анкету/диагностику/подписанные URL документов любого пользователя.
17. `SERVICE_ROLE_KEY || ANON_KEY` в 4 местах — тихая деградация.
18. `logAudit` глотает ошибки; у журнала нет UI.

# ИТОГОВЫЙ ОТЧЁТ GIGA-CRM (2026-09-17, вечер)

## A. Архитектура
- **RBAC персонала** — `lib/admin/rbac.ts` (6 ролей × 28 прав, код, а не данные) + `staff_roles` (073). Каждый `/api/giga-admin/*` маршрут вызывает `requireGiga(req, permission)`; мутации дополнительно проходят проверку Origin (CSRF) и ранга цели (`canManageTarget`: нельзя трогать равных/старших).
- **Актор** — `lib/admin/giga-actor.ts`: личная сессия (super_admin или роль из `staff_roles`) → короткий личный staff-cookie (выдаётся при входе «от имени», роль перечитывается из БД) → аварийный общий пароль.
- **Журнал** — `admin_audit_log` (append-only, триггер запрещает UPDATE/DELETE/TRUNCATE), `recordAdminAction(..., { required: true })` пишется ДО разрушающих операций. Старый `logAudit` пишет в оба журнала; 2 старые записи перенесены.
- **События** — `user_events` + реестр `lib/events/registry.ts` (клиентские события отмечены флагом, серверные нельзя подделать), `POST /api/v1/events`, `ActivityTracker` в кабинете, серверные события в анкете/GRI/документах/Точке А/входе. `profiles.last_seen_at`.
- **История анкеты** — триггер `survey_answer_history`: автор берётся из JWT пользователя или из заголовков `x-actor-*` (доверяются только service_role); правки склеиваются в окне 10 минут.
- **Impersonation** — `impersonation_sessions` (30 мин), сессия пользователя создаётся на сервере (magic-link не покидает сервер), подписанный httpOnly-cookie режима; middleware: режим «просмотр» блокирует любые записи (403), каждая запись в режиме «правка» аудитируется, истёкшая/закрытая сессия разлогинивает браузер; баннер + рамка + «Выйти из режима пользователя».
- **CJM** — этапы считаются по фактам (SQL `admin_journey_stages`, TS `lib/admin/journey.ts`); действия админов в кабинете не двигают клиента по этапам (075).
- **CMS и разделы** — `cms_pages/cms_blocks/cms_page_revisions`, бакет `cms-media`, `platform_sections`; правила видимости `lib/platform/visibility.ts` (все / сегменты any|all / только персонал, ошибочное правило = скрыто); выключенный или скрытый раздел исчезает из меню и блокируется в middleware.

## Анкеты, настройки платформы и исправления (2026-09-17, 18:00–19:00)

### Раздел «Анкеты»
Показывает всех пользователей (фильтры, сегменты, статус, сортировка «Недавно изменённые» — миграция 079). При наведении — мини-карточка с кратким профилем, по клику — окно с ответами и действиями: открыть анкету в кабинете (вход от имени пользователя), редактировать, добавить или удалить ответ, удалить всю анкету (ввод «УДАЛИТЬ» и причина). Все действия записываются в журнал аудита.

### Настройки платформы (`/admin-giga-panel/settings`)
Единый реестр `lib/settings/registry.ts` (схема, значение по умолчанию и описание для каждой настройки) и общий API `GET/PUT /api/giga-admin/settings`. Изменения проверяются, в журнал аудита пишется «было → стало» до записи, а если журнал недоступен, запись не выполняется. Каждая настройка влияет на реальное поведение платформы:

| Настройка | Где действует |
|---|---|
| Режим регистрации, авто-одобрение, тарифные ограничения, модерация ИИ | прежние getter-функции (значения пользователя сохранены) |
| Число полных GRI на тарифе Free | `readEntitlements` → `/api/v1/access/me` (`griRunsLimit`), `/api/v1/gri/assessment` (402) |
| Объявление в кабинете | `AnnouncementBar` в layout кабинета и дашборда; ссылки только `/…` или `https://` |
| Режим техработ | middleware → `/maintenance` для client/owner; панель управления и вход «от имени» работают; страница сама возвращает в кабинет |
| Правка «от имени» и длительность сессии | `POST /api/giga-admin/impersonation` |
| Обязательная 2FA для персонала | middleware → `/settings?tab=security&mfa=required` |
| Аварийный вход по общему паролю | `/api/giga-admin/auth`, `getGigaActor`, middleware; выключить можно только из личного аккаунта |
| Сбор поведенческой аналитики | `/api/v1/events` (ключевые события пишутся всегда) |
| Срок хранения событий + «Очистить старые события» | `/api/giga-admin/system/purge-events` (аудит, ввод «УДАЛИТЬ») |
| Уведомления администраторам по типам | `notifyAdmins` |
| Состояние системы | `/api/giga-admin/system/health`: переменные окружения (только признак «настроено»), таблицы, бакеты, среда |

Проверено сквозным HTTP-сценарием: сессия по общему паролю и отдельная сессия QA-клиента, 24 проверки. Все значения пользователя возвращены.

### Баг «после техработ не зайти в кабинет»
Корень — кеш Next.js (Data Cache): он сохранял ответ service-клиента Supabase на запрос `system_settings`. Страница `/maintenance` показывала «доступен», middleware продолжал перенаправлять, а сохранение сравнивало новое значение с устаревшим и пропускало запись как «без изменений».

Исправления:
- `createServiceClient` / `createActorServiceClient` работают с `cache: 'no-store'`;
- панель, сохранение, страница техработ и `/api/v1/platform/maintenance` читают настройки из базы напрямую;
- кеш настроек сокращён до 5 с;
- страница техработ опрашивает статус и возвращает пользователя полной перезагрузкой.

После выключения кабинет открывается через 2–6 с.

### Попутно
- **Метрики не записывались.** `materialize.ts` ссылался на 5 колонок в `onConflict`, а прод-индекс `metrics_unique_idx` содержит 7 (`NULLS NOT DISTINCT`). Код исправлен; миграция **080** выравнивает индекс в базах, собранных с нуля (на проде ничего не меняет). Интеграционный тест на реальной базе проходит.

- **Зависимости.** В локальном `node_modules` не было `@dnd-kit/*` и `@vercel/functions` (сборка падала) — установлены по lock-файлу.
