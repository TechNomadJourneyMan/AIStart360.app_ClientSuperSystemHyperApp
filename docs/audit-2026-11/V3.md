# V3 — SR-01: права персонала в RLS только для живой сессии со step-up (миграция 143)

Ветка `claude/multi-agent-portal-dev-8f4869`. Ничего не закоммичено. Миграция применялась только к локальной тестовой БД.

## Решение

**БД (`supabase/migrations/143_staff_mfa_sessions.sql`)**

- Таблица `public.staff_mfa_sessions`:
  - колонки: `session_id uuid PK`, `user_id → auth.users ON DELETE CASCADE`, `verified_at`, `expires_at`, `method`;
  - RLS включён, политик нет;
  - `REVOKE ALL` у PUBLIC, anon и authenticated; права только у service_role.
- `public.staff_session_ok()` (SECURITY DEFINER, `search_path = public`) возвращает true, если выполнены оба условия:
  - (а) `auth.jwt()->>'session_id'` — валидный uuid, сессия есть в `auth.sessions` у этого `auth.uid()` и `not_after` не прошёл (при выходе или отзыве GoTrue удаляет строку);
  - (б) если 2FA для этого человека обязательна, есть неистёкшая запись `staff_mfa_sessions` по этим session_id и user_id. Обязательна она, когда выполнено любое из:
    - `system_settings.staff_require_mfa` = `true` или `{"enabled":true}`;
    - `user_security.totp_enabled`;
    - есть passkey;
    - в `app_metadata` стоит `mfa_totp` или `mfa_webauthn`.
- Через `CREATE OR REPLACE` переписаны три хелпера из 140, которые читают `staff_roles`/`profiles.role`: `current_staff_role()`, `is_active_expert()`, `staff_sees_all_clients()`.
  - Все остальные хелперы и политики 140 построены на них и наследуют проверку: `is_platform_admin`, `is_platform_staff`, `staff_/expert_assigned_user_ids`, `staff_can_read_company`, ветки персонала в `can_read_company` и `accessible_company_ids`, все переписанные политики, триггеры-обходы.
  - Проверка стоит внутри `CASE` по найденной строке. Поэтому для клиентов `staff_session_ok()` не вызывается вообще: ни затрат, ни изменений поведения.
- Клиентские, owner-, member- и partner-политики не тронуты. service_role не затронут: у него `auth.uid()` = NULL, и хелперы и так были NULL.
- Предусловия проверяются в начале миграции, при нарушении она прерывается с понятным текстом:
  - `auth.sessions` существует, есть колонки `id`, `user_id`, `not_after`;
  - у роли миграции есть SELECT на `auth.sessions`;
  - 140 уже применена.
- Откат: `supabase/migrations/rollback/143_staff_mfa_sessions.down.sql`. Возвращает тела трёх функций ровно в версии 140, удаляет функцию и таблицу. Проверен на тестовой БД.

**Сервер (fail closed)**

- `lib/mfa/step-up-session.ts`:
  - `recordStepUpSession` делает upsert через service-role со сроком cookie (`STEP_UP_TTL_MS` = 12 ч) и попутно чистит истёкшие записи пользователя;
  - `issueStepUp` сначала пишет запись, потом ставит cookie;
  - `forgetStepUpSession` / `forgetStepUpSessionsOfUser`;
  - `stepUpFailure` даёт ответ 503 «Код принят, но подтвердить вход не удалось… Повторите через минуту», а для `no_session` — 401 «Сессия не найдена. Войдите заново».
  - Токен без `session_id` (`nosid`) step-up не получает — это заодно закрывает SR-16.
- Места выдачи step-up:
  - `2fa/challenge` (TOTP и резервный код): сначала запись, потом код списывается. Если запись не прошла, код не тратится. Если не прошло списание, запись откатывается;
  - `webauthn/authenticate/verify`;
  - первый фактор в `2fa/verify` и `webauthn/register/verify`: фактор уже сохранён, поэтому без записи cookie не ставится, а ответ `{ok:true, step_up:false, notice}`. Middleware при следующем переходе отправит на /2fa.
- Удаление записей:
  - `2fa/disable` — запись этой сессии;
  - `v1/auth/sign-out` (global) и `settings/sessions/revoke-all` — все записи пользователя.
  - Удаление best-effort: отсутствие строки в `auth.sessions` само по себе обнуляет права.
- Версия step-up cookie поднята v2 → v3 (`step-up.ts`, `step-up-edge.ts`). Без этого старые cookie остались бы валидны для приложения, но без записи в БД персонал до 12 ч видел бы пустые экраны. После выката все с фактором один раз проходят 2FA заново: middleware стирает невалидный cookie и ведёт на /2fa.
- Dev: `lib/dev/dev-step-up.ts`.
  - `/api/dev/login` пишет запись с `method='dev'` по токену, который только что выдан.
  - `/api/dev/mode` при on пишет запись для сессии, подтверждённой через `getUser`, при off удаляет только dev-запись.
  - Сбой только логируется. В production-сборке ветка мёртвая.
  - Учтите: dev работает с прод-БД, поэтому dev-записи попадут в прод-таблицу, когда 143 там будет.

**Где пользователь увидит пустоту вместо перехода на /2fa** (это зона V1, `middleware.ts`; я его не трогал):

- (a) Общая проверка страниц `middleware.ts:631-646` (`/dashboard`, `/clients/*`, `/expert/*`) не применяет `staff_require_mfa`. При включённой настройке сотрудник без фактора проходит в middleware, а БД ему откажет. Нужно перенести правило `enroll`, как это сделано для `/admin-giga-panel` и `/super-expert`.
- (b) Все проверки middleware (`:543`, `:579`, `:631`) смотрят только флаги в JWT (`mfaFlagsEnrolled`). Если фактор появился после выдачи токена, БД и API уже требуют step-up, а страница — нет. Пусто будет до обновления токена, не дольше 1 ч.
- (c) Dashboard (№1, 2) не может отличить «срезано RLS» от настоящих нулей. Лучше перевести вид персонала на service-role + `requireGiga`/скоуп или убрать его в пользу панели.
- (d) Dev: если войти паролем через /login и включить dev-режим cookie, минуя `/api/dev/mode`, записи не будет. Через dev-панель запись создаётся.

**Попутная находка** (service-role, 143 её не закрывает): `/api/v1/action-plan` GET `?userId` и `/api/v1/action-plan/[id]` PATCH читают и правят `action_items` любого клиента. Проверяется только legacy `profiles.role`, без 2FA и без скоупа. Вызываются из `components/expert/tabs/PointBTab.tsx:114` и `components/giga-panel/user360/PointBTab.tsx:67`. Это класс SR-02/SR-03.

## План применения на прод (140 → 143)

Перед стартом (только чтение, прод-БД):

1. В `schema_migrations` есть 140, проверки отчёта A2 пройдены. 143 сама откажется без 140.
2. `SELECT has_table_privilege('postgres','auth.sessions','SELECT')` возвращает true; колонки `id`, `user_id`, `not_after` есть: `SELECT column_name FROM information_schema.columns WHERE table_schema='auth' AND table_name='sessions'`.
3. `SELECT count(*), max(created_at) FROM auth.sessions` — сессии пишутся. JWT содержит `session_id`: старый формат step-up уже отвергается, значит, у текущего GoTrue он есть.
4. Посмотреть, кому понадобится step-up:
   - `SELECT key, value FROM system_settings WHERE key='staff_require_mfa'`;
   - у кого из персонала и экспертов есть фактор: `user_security.totp_enabled` / `webauthn_credentials` по `staff_roles` + `profiles.role='expert'`.
   - Предупредить их, что после выката 2FA придётся пройти один раз заново.
5. Решить с PO, включать ли `staff_require_mfa`. Рекомендация SEC-REVIEW-2 §3 — включать вместе с 143.

Применение (одно окно, без паузы между шагами):

6. `node scripts/apply-migration.js supabase/migrations/143_staff_mfa_sessions.sql` (одна транзакция; `lock_timeout` 5 с).
7. Сразу выкатить приложение с этим кодом (redeploy main на Railway).
   - До выката старый код записей не пишет, и персонал с фактором видит пустые экраны из таблицы выше. Экраны на service-role (панель, эксперт-API) работают.
   - Обратный порядок недопустим: новый код без таблицы не выдаст step-up никому, у кого есть фактор.

После:

8. `SELECT staff_session_ok()` от anon возвращает false. `\dp public.staff_mfa_sessions` — прав у anon/authenticated нет.
9. Тестовый сотрудник с TOTP:
   - вход, /2fa → в `staff_mfa_sessions` появилась строка;
   - панель и экраны эксперта открываются;
   - прямой запрос `GET /rest/v1/survey_answers` с его JWT до step-up возвращает `[]`, после — данные;
   - после «Выйти» тот же JWT возвращает `[]`.
10. Клиент: кабинет, анкета, документы работают как раньше. Это smoke-проверка клиентского пути.
11. Следить в логах за `[2fa/challenge] step-up record failed` и 503 на `/api/v1/security/*`.

Откат:

- Сначала откатить приложение. Затем `node scripts/apply-migration.js supabase/migrations/rollback/143_staff_mfa_sessions.down.sql`. Это снова открывает SR-01.
- Если откатывается только БД, а новый код остаётся, step-up перестанет выдаваться (fail closed). В таком случае вместо полного отката вернуть только тела трёх функций: первые три блока down-файла, без `DROP TABLE`.
