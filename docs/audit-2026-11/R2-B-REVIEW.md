## Находки по убыванию серьёзности

### 1. ВЫСОКАЯ — SuperExpert с правилом «только назначенные» может забрать себе клиента вне своего скоупа (обход отзыва доступа)
- **Где:** `app/api/giga-admin/expert-sla/[id]/route.ts:41-56`, `lib/expert-sla/store.ts:57-60` (`visibleTo`), `lib/expert-sla/store.ts:149-177` (`reassignClientWork` → `setClientAssignment`).
- **Сценарий:**
  1. SuperExpert S, `staff_roles.client_scope = 'assigned'`, был ответственным клиента X. На X была открытая SLA-задача, назначенная на S (`assigned_via = 'client'`).
  2. Admin передаёт X другому человеку: «Пользователи» → `PUT /users/:id/assignment`.
  3. Задача остаётся на S (см. находку 2). PATCH проверяет только `visibleTo`, а `visibleTo` даёт `true`, если `assignee_id === actor.id`.
  4. S вызывает `PATCH /api/giga-admin/expert-sla/<task> {assigneeId: S}` («Взять себе»). Срабатывает `setClientAssignment(X → S)`.
  5. **Итог:** S снова ответственный X. У S снова полный доступ к данным X: RLS `staff_assigned_user_ids`, `mayActOnUser` и вход под клиентом (`impersonate.view/edit` есть у super_expert). Отзыв доступа администратором обойдён.

  Штатный путь `PUT /users/:id/assignment` вызывает `guardClientAccess` и S бы отказал. S может так же передать X любому эксперту.

  Другие способы получить «свою» задачу чужого клиента:
  - клиент сам ставит `assignee_id = S` в своём обращении (находка 3, пробы P1/P5);
  - кто-то назначил кейс на S в «Эскалациях» — sync 4.3 переносит задачу.
- **Уверенность:** подтверждено кодом. Проба P5 показала, что задача клиента C переходит на S (`reassigned`), а C за S не закреплён. Unit-тест `routes.test.ts` проверяет только задачу, не назначенную на S. Нужный тест: `s.scope = {scope:'assigned', clientIds:[]}`, задача T с `assignee_id = SE` и `client_id = C3`, PATCH `{assigneeId: SE}` → ожидается 403, сейчас будет 200.
- **Исправление:** для смены ответственного клиента в PATCH требовать `scopeAllows(scope, task.client_id)` (или `guardClientAccess(actor, task.client_id)`). Видимость по `assignee_id` оставить только на чтение. Плюс исправить находку 2.

### 2. СРЕДНЕ-ВЫСОКАЯ — задачи не переходят за сменой ответственного клиента: бывший исполнитель продолжает видеть задачи и получать по ним эскалации
- **Где:** миграция 145, sync 4.3 (`145_…sql:301-316`) переносит только кейсы при смене `expert_cases.assignee_id`. На смену `user_assignments` не реагирует никто: ни sync, ни `setClientAssignment`, ни массовое назначение, ни бот. В RLS ветка `assignee_id = auth.uid() AND is_platform_staff()` (`145_…sql:131`). В API — `visibleTo` (`store.ts:59`), его вызывает `/api/expert/sla-tasks:34`.
- **Сценарий (проба P2):**
  1. Клиент D, ответственный — эксперт E1, отчёт на проверке. sync создаёт задачу на E1 (`client`).
  2. Admin переназначает D на E2. Следующий sync ничего не меняет: задача остаётся на E1.
  3. E1 через RLS по-прежнему читает задачу D: заголовок, `client_id`, `company_id`. Его очередь `/expert/queue` её тоже показывает, с именем компании.
  4. Через 24 ч эскалация уходит к E1 (`assignee_notified = e1`): лента, экспертный Telegram, имя клиента. E2 задачу видит, но не как «Мою» и уведомлений не получает.
- **Уверенность:** подтверждено пробой P2.
- **Исправление:**
  - в sync для открытых задач с `assigned_via IN ('client','auto')` выравнивать `assignee_id` по `user_assignments`, если там исполнитель SLA (worker); иначе снимать исполнителя → очередь;
  - либо триггер на `user_assignments`;
  - в RLS и `visibleTo` для персонала со скоупом «назначенные» и для экспертов ограничить ветку по исполнителю клиентами из скоупа (`client_id IN staff_assigned_user_ids()`) или убрать её.

### 3. СРЕДНЯЯ — клиент сам задаёт исполнителя и статус своего обращения, а SLA этим полям доверяет
- **Где:**
  - `032_smart_assistant.sql:112-113`: политика `expert_cases_insert_own` — `WITH CHECK (user_id = auth.uid())`. У роли authenticated есть INSERT на всю таблицу (проверено в тест-БД);
  - `145_…sql:343-347`: `own` становится исполнителем, если он worker;
  - `145_…sql:279, 326-327`: `status = 'in_progress'` или `first_response_at` засчитываются как реакция;
  - `run.ts:108`: кейс с `assigned_via = 'source'` не получает уведомления о назначении.
- **Сценарий (проба P1):**
  1. Клиент C прямым запросом PostgREST создаёт `expert_cases` с `assignee_id = E2`, где E2 — любой эксперт, SuperExpert или Admin.
  2. Задача создаётся на E2 (`source`), минуя авто-назначение и общую очередь. SuperExpert про «задачу без исполнителя» не узнаёт.
  3. E2 видит задачу с придуманным клиентом заголовком, но сам кейс и данные клиента ему недоступны (`e2 sees the case itself = 0`). Работа повисает до эскалации через 24 ч.
  4. Эскалация несёт текст клиента в Telegram E2, SuperExpert и Admin. HTML экранирован, но это канал спама.

  Вставка с `status = 'in_progress'` полностью отключает эскалацию по реакции для этого обращения (вредит только самому клиенту). В сочетании с находкой 1 клиент может «пригласить» SuperExpert, и тот заберёт клиента вне скоупа.
- **Уверенность:** подтверждено пробой P1.
- **Исправление:**
  - отозвать INSERT на `expert_cases` у authenticated: приложение создаёт обращения через service role (адаптер `internal-adapter.ts`, `createCommCase`);
  - либо выдать права только на нужные колонки, либо триггером BEFORE INSERT для не-service ролей обнулять `assignee_id`, `assigned_to`, `first_response_at` и ставить `status = 'new'`;
  - в sync принимать `own` как исполнителя, только если он одновременно ответственный клиента или staff со скоупом `all`.

### 4. СРЕДНЯЯ — авто-назначение раздаёт экспертам доступ без проверки, что «клиент» действительно клиент; включено по умолчанию и не пишется в журнал
- **Где:** `lib/expert-sla/run.ts:111-140`, `lib/expert-sla/assign.ts:104-120`, миграция 145, sync 4.4 (никакого фильтра по роли или статусу клиента), `lib/settings/registry.ts:190` (`enabled: true, auto_assign: true`).
- **Сценарий:**
  1. У аккаунта super_admin (или другого сотрудника, эксперта, заблокированного или неодобренного пользователя) есть своя компания с рекомендациями на проверке, отчётом или обращением, а ответственного нет.
  2. Проба P4: sync создаёт задачу `rec_review` с `client_id = super_admin` без исполнителя.
  3. Следующий проход делает наименее загруженного эксперта «ответственным» этого аккаунта (`user_assignments`).
  4. Эксперт получает доступ к его данным через RLS 140 и `mayActOnUser`, включая API `/api/v1/*?userId=` с записью.

  Сразу после деплоя всех клиентов с ожидающими рекомендациями (их «много») автоматически закрепят за 1–2 экспертами. Правило 140 «эксперт видит только назначенных» на практике станет «эксперт видит почти всех». Это решение вопроса PO №1, принятое до его ответа.

  Запись в журнал аудита `admin_audit_log` (`recordAdminAction`) не делается: только `assigned_by = 'system:expert-sla'` в `user_assignments`.
- **Уверенность:** P4 подтверждена пробой. Остальное следует из кода.
- **Исправление:**
  - авто-назначать только обычных клиентов: `profiles.role` клиентская, нет строки `staff_roles`, `status = 'approved'`;
  - по умолчанию `auto_assign: false` до ответа PO;
  - писать запись аудита `user.assigned` от имени системы.

### 5. СРЕДНЯЯ — первый проход нарушает бюджет ≤ 45 с и устраивает лавину уведомлений
- **Где:**
  - `run.ts:144`: `for (const t of assigned) await notifier.assigned(t)` — без бюджета и без сводки;
  - `notify.ts:165-173` и `145-154`: на задачу 4–5 последовательных запросов к БД плюс Telegram с таймаутом до 8 с;
  - `run.ts:102`: `.in('id', newIds)`;
  - `run.ts:112`: при `over()` задача уходит в очередь навсегда.
- **Сценарий:**
  1. На первом проходе sync создаёт до 200 задач на каждый из 4 источников, то есть до 800.
  2. Все задачи `report_review` и `rec_review` клиентов, у которых ответственный — эксперт, уведомляются **по одной**: лента и экспертный Telegram. «Больше 5 — одна сводка» сделано только для `queued` и порогов.
  3. На 100–300 задач это минуты: при сбое Telegram 300 × 8 с. Это выходит и за ≤ 45 с, и за `finish: '2m'`. По `lib/functions/limits.ts` после этого рядом может стартовать второй проход.
  4. Telegram отвечает 429 на лимит «1 сообщение в секунду в чат», часть сообщений теряется. Эксперт получает сотни личных сообщений.
  5. Задачи, до которых не дошёл бюджет авто-назначения, навсегда уходят в «Без исполнителя» с уведомлением SuperExpert: повторного авто-назначения нет. То же при сбое `loadExpertCandidates`.
  6. *Предположение:* URL `.in('id', 800 UUID)` занимает около 30 КБ. Если запросы идут через Kong/nginx с буфером строки 8 КБ, чтение упадёт (414) уже после sync. Тогда созданные задачи никогда не будут авто-назначены. Нужно проверить на staging.
- **Уверенность:** нарушение бюджета и отсутствие сводки для `assigned` подтверждены кодом. 414 — предположение.
- **Исправление:**
  - группировать `assigned` по исполнителю и при > BATCH отправлять одну сводку;
  - проверять бюджет в цикле уведомлений;
  - отдавать колонки задач прямо из RPC, без второго чтения;
  - не ставить «очередь» при исчерпании бюджета: оставлять задачу с пометкой ожидающего авто-назначения и брать её на следующем проходе.

### 6. СРЕДНЯЯ — эскалация может потеряться и не повторяется
- **Где:** `run.ts:150-154`: порог захватывается и коммитится до отправки. `notify.ts:156-162`: `safe` глотает любые ошибки. `notify.ts:137`: при ошибке чтения адресатов получается `{[],[]}`. `lib/notifications/staff.ts:271`: при непустом `audienceUserIds`, даже `[]`, служебные чаты из env пропускаются.
- **Сценарий:**
  1. `expert_sla_claim` выставил `escalated_at` / `breached_at`.
  2. Дальше любой из случаев:
     - Prisma или БД мигнула: `recordEvent` бросил исключение, его проглотили, в ленте ничего нет;
     - чтение `staff_roles` вернуло ошибку: адресатов нет, Telegram персоналу не уходит;
     - процесс перезапустился или упал по OOM между захватом и отправкой.
  3. **Итог:** эскалация отмечена как отправленная, но никто её не получил. Следующий проход её не повторит. Отчёт признаёт это («не повторяется при сбое канала»), но это главная функция механизма.
- **Уверенность:** подтверждено кодом.
- **Исправление:** две фазы — `escalated_at` (захват) и `escalation_notified_at` (доставка). Задачи, захваченные более N минут назад и не доставленные, отправлять повторно; ключ дедупликации ленты уже есть. Альтернатива — outbox.

### 7. СРЕДНЕ-НИЗКАЯ — старт часов SLA фиксируется в момент миграции, а не в момент первого прохода
- **Где:** `145_…sql:134-137`. В sync `received_at = greatest(ts, clock_start)`.
- **Сценарий:** миграция применяется при пуше в main, а Inngest-функция появляется только после ручного resync (`PUT /api/inngest`, отчёт R2-B §4) или после включения `enabled`. Если между ними прошло больше 48 ч, на первом проходе **весь бэклог сразу просрочен** (breached), а метрики SLA испорчены. Это противоречит цели «бэклог не превращается в лавину» и ответу на вопрос PO №4.
- **Уверенность:** подтверждено кодом.
- **Исправление:** записывать `expert_sla_clock_start` в sync при первом запуске (`INSERT … ON CONFLICT DO NOTHING` с `v_now`), а не в миграции.

### 8. НИЗКО-СРЕДНЯЯ — «ответ» засчитывается без участия эксперта, а пересборка сбрасывает часы
- **Где:** `145_…sql:205-224` (report), `226-245` (plan), `247-267` (rec).
- **Сценарий:**
  - **P3:** рекомендации компании F ушли в `stale`, потому что изменились входные данные. Никто их не проверял, а задача закрыта с `close_reason = 'reviewed'`, реакция и ответ засчитаны.
  - **P2b:** отчёт на проверке стал `superseded` (новая версия). Задача закрыта как «ответ», а для новой версии открывается новая задача с новыми 48 ч.
  - Если агент пересобирает отчёт чаще раза в 48 ч, эскалация по нему не наступит никогда.
  - Для рекомендаций `markStale` и новая генерация — отдельные операции. Если sync попадает между ними (ИИ-генерация может идти десятки секунд), происходит то же самое.
- **Уверенность:** P2b и P3 подтверждены пробами. Частота пересборки — предположение.
- **Исправление:**
  - закрывать с отдельной причиной (`superseded`/`stale`) и не считать это ответом и реакцией;
  - для новой версии того же отчёта или рекомендаций той же компании переносить `received_at` и дедлайны со старой задачи.

### 9. НИЗКАЯ — ошибка sync останавливает все эскалации
- **Где:** `run.ts:88`. Ошибка `expert_sla_sync` бросается до `expert_sla_claim`.
- **Сценарий:** ошибка любого из 12 запросов внутри sync отключает пороги для **уже открытых** задач, хотя захват от sync не зависит. Примеры: нарушение CHECK или FK на одной строке, отсутствующая колонка источника в одном окружении, таймаут.
- **Исправление:** выполнять захват порогов и отправку независимо от исхода sync, ошибку sync логировать и поднимать уведомление отдельно.

### 10. НИЗКАЯ — п. 4 (текст клиенту): обещание завязано на настройку, а не на реально работающие часы
- **Где:** `lib/comm/bot.ts:338-346, 457-459`, `lib/comm/bot.ts:255-263` (`createCommCase` возвращает уже открытый кейс), `app/api/v1/expert-sla/route.ts:51`.
- **Что верно:** в боте «Оформил заявку. Эксперт ответит в течение 48 часов.» действительно выводится только при `caseId` (обращение записано) и `expert_sla.enabled`. Порядок «сначала заявка, потом ответ» соблюдён.
- **Сценарии неточного обещания:**
  - настройка по умолчанию `enabled: true`, поэтому обещание показывается и тогда, когда миграция 145 ещё не применена, Inngest не пересинхронизирован или сделан откат 145. Задача в SLA не создаётся, часов нет;
  - `createCommCase` вернул **существующий** открытый кейс: клиенту снова обещают 48 ч, хотя его задача может быть уже просрочена;
  - `/api/v1/expert-sla` выдаёт обещание и по `plan_review` (одобряет Admin, а не эксперт), и по уже просроченным задачам;
  - обещание дописывается к ответу LLM, где может стоять «эксперт свяжется, как только освободится» — получается противоречие.
- **Исправление:**
  - показывать обещание, только если последний успешный проход SLA был не позже ~15 минут назад (метка от `run`);
  - для существующего кейса считать остаток по его `answer_due_at`;
  - в `/api/v1/expert-sla` не учитывать `plan_review` и просроченные задачи.

### 11. НИЗКАЯ — прочее
- `app/api/giga-admin/cases/[id]/route.ts:59-61`: теперь можно назначить кейс эксперту, который не ответственный клиента. sync 4.3 переносит на него задачу, но данных клиента он не видит (как в P1): задача невыполнима. Нужно либо требовать, чтобы эксперт был ответственным клиента, либо делать то же, что `reassignClientWork`.
- RLS клиента (`145_…sql:121-123`) отдаёт через PostgREST все колонки своих строк: `assignee_id`, `escalated_at`, `breached_at`, `close_reason`, внутренние заголовки. API их скрывает, а прямой REST — нет. Можно выдать права по колонкам или сделать представление.
- Не сделано: задачи эксперта, которого заблокировали или лишили одобрения, остаются на нём. Во вкладку «Без исполнителя» они не попадают, хотя эскалации SuperExpert получит.
- `lib/admin/actor-scope.ts:38-41` (существовало и раньше): при ошибке чтения `staff_roles` скоуп считается `all`, и новые маршруты ГИГА наследуют это открытие при сбое.
- `loadSlaTasks` молча обрезает список клиентов до 1000 (`store.ts:99`), и URL `.or(client_id.in.(…1000 UUID…))` очень длинный. С тем же предположением про лимит шлюза, что в находке 5: при авто-назначении «почти всех» клиентов очередь эксперта может отдавать 503.
