- **(а) Уборка зависших и захват «Повторить».** Нормальный автоматический путь не блокируется:
  - снимок вставляет новую строку `processing` без захвата;
  - внутренний вызов `ai-analyze` (по токену) сам ставит `processing` и `ai_started_at=now` без условий;
  - `catchUpPaidAi` захватывает строку с `cooldownMs:0` и отказывается только при живом `processing` или `completed`.

  Живой разбор не помечается `stale`: `cas.sh` — строка с `ai_started_at` 2 мин назад и `calculated_at` 3 ч назад не тронута, 14 мин — не тронута. Разбор длится ≤ 120–150 с при пороге 15 мин.

  Если уборка всё же сработает на живом разборе (сценарий, который мы не обнаружили), итог разбора перезапишет `failed`, данные не теряются. Остаточный риск — повторный «Повторить» в этом окне. Это узкий случай, не дефект.

## 3. Новые дефекты

### N0 (High, миграция 152 в коммите 9a528de4) — на настоящем Supabase весь проход SLA падает с 42501
- **Где:**
  - `152_expert_sla_ai_review_plan_prep.sql` (версия 9a528de4), `expert_sla_open_ai_review` (стр. 251) и `expert_sla_plan_prep` (стр. 360) — `EXISTS (SELECT 1 FROM auth.users …)`;
  - обе функции SECURITY INVOKER и вызываются сервисной ролью;

  До 152 SLA-функции читали `auth.users` только через FK (145), а FK привилегий не требует.
- **Сценарий:** у `service_role` нет SELECT на `auth.users` (по заметке другой сессии, так на staging 2026-11-15). Тогда каждый вызов `expert_sla_sync` → `permission denied for table users`, и весь проход SLA (кейсы, отчёты, планы R2) не работает. Права проверяются при запуске запроса, поэтому падает даже на пустой базе. Немедленный путь `announceAiReviewNow` ошибку молча проглатывает.
- **Подтверждено:** временная база `r3verify_head`: все миграции, 152 — ровно из 9a528de4.
  - `REVOKE ALL ON auth.users FROM service_role, PUBLIC`, затем `SET ROLE service_role`;
  - `expert_sla_sync(now(),24,48,200)` → `ERROR: permission denied for table users`;
  - `expert_sla_open_ai_review(…)` → то же.

  Наши тесты этого не видят: заглушки тест-БД (`scripts/test-db/supabase-stubs.sql`) дают `service_role` SELECT на `auth.users`. Само наличие такого права на staging и проде я не проверял — staging не трогал.
- **Статус:** во время моей проверки (22:47) **другая сессия** правит это в рабочем дереве, изменения не закоммичены:
  - 152: обе функции → `SECURITY DEFINER SET search_path = public`, EXECUTE по-прежнему только у `service_role`;
  - `immediate.ts` теперь логирует ошибку RPC;

  Эту правку я не проверял как выкатываемую версию. По чтению она закрывает дефект. Справочно: для SECURITY DEFINER принято `search_path = public, pg_temp`; при EXECUTE только у `service_role` риск минимальный. **В коммите 9a528de4 дефект есть.**

### N2 (Medium) — после того как эксперт или админ внёс хотя бы один показатель месяца, владелец не может сохранить «Факт за месяц» вообще

  4. Тело запроса: `{revenue: 7000000, leads: 300}` → 400 «Выручка за месяц: это значение за месяц внёс эксперт…». Лиды не сохранены.
  5. Очистить поле выручки тоже нельзя: уходит `revenue: null` → тот же отказ.

  Владелец заперт на весь месяц. Обратная сторона: форма персонала тоже отправляет все предзаполненные значения владельца, и `upsert` перемечает их как `entered_role='expert'`. Одно сохранение админом блокирует владельцу все показатели месяца.
- **Подтверждено:** `pb-m1.verify.test.ts`, тест «NEW…»:
  - `initial {"revenue":7000000}`;
  - тело формы `{"revenue":7000000,"leads":300}`;
  - ответ `PlanFactError … [revenue]`;
  - лиды в БД — `null`.
- **Предложение:**
  - на сервере отказывать, только если значение эксперта действительно **меняется** (сравнивать с сохранённым), а неизменённые пропускать без перезаписи `entered_role`;
  - в форме не отправлять неизменённые значения и показывать поля эксперта только для чтения;
  - то же правило — для формы персонала: не перемечать неизменённые значения владельца.
- **Уверенность:** высокая.

### N1 (Medium) — массовая смена тарифа запускает догонку гипотез ИИ для всех клиентов одновременно, мимо пула 2
- **Где:** `lib/point-a/diagnostic-row.ts:151–155` — новый `void runInBackground('point-a-hypotheses-catch-up', …)` внутри `catchUpPaidAi`. `catchUpPaidAiAwaited` / `catchUpPaidAiBatch` (`lib/point-a/catch-up-batch.ts`, правило «не больше 2 одновременно» после инцидента 504 от 2026-10-15) ждут только вызовы fan-out, но не эту работу.
- **Сценарий:**
  1. ГИГА → массово «Сменить тариф → Pro» для 200 Free-клиентов (`lib/admin/bulk-users.ts:226`).
  2. У Free-клиентов гипотез не было, поэтому у каждого есть блоки, которым нужна гипотеза.
  3. Пул 2 быстро пробегает список, а 200 фоновых генераций гипотез (последовательные вызовы модели по блокам, каждая под бюджетом) идут параллельно на сервере с 8 ГБ.
- **Подтверждено:** `pa-catchup.verify.test.ts` — 8 клиентов через пул 2: **пик 8 одновременных** задач гипотез. Пакет завершился, когда готово было 0 из 8.
- **Предложение:** передавать гипотезы в тот же `track` / `works` (`catchUpPaidAiAwaited` ждёт и их) или запускать их внутри слота пула. При единичном переходе на платный тариф (биллинг, ГИГА по одному) это не проблема.
- **Уверенность:** высокая — по механике. Насколько это опасно на проде, зависит от числа клиентов в пакете.

### N3 (Low) — гонка: эксперт подтверждает разбор, который был перегенерирован в той же строке, пока у него была открыта проверка
- **Где:** `lib/point-a/ai-review-store.ts:151–163`. Оптимистическая проверка сравнивает только `is_current` и **текущий** (только что прочитанный) `ai_status`. Версию текста, которую видел эксперт, клиент не присылает: в теле нет `ai_generated_at` или хеша. Комментарий модуля обещает «The row was regenerated meanwhile → 409», но это верно только для новой строки (пересчёта) или для `processing`.
- **Сценарий:**
  1. Задача `pa_ai_review` открыта по частичному разбору (`failed` + текст).
  2. Эксперт открыл проверку.
  3. Владелец нажал «Повторить», через ~2 мин в той же строке готов новый текст (`NO_REVIEW` снял отметку).
  4. Эксперт нажимает «Подтвердить».
  5. Ответ — ok. Вся форма со **старым** текстом записана как «правки эксперта». Клиент видит «Проверено экспертом» со старым текстом во всех полях с пометкой «поправлено экспертом», а новый блок, которого эксперт не видел, — тоже под отметкой.
- **Подтверждено:** `sla-review.verify.test.ts`, тест «race»:
  - `ok (confirmed)`;
  - `summary:"OLD: резюме"`;
  - `edited` = все 6 полей;
  - `marketing:"NEW d"` под `review:"Пётр Эксперт"`.
- **Предложение:** передавать в PUT/POST `generatedAt` (или хеш `ai_analysis`), который видел эксперт, и включать его в условный UPDATE. При расхождении — 409 «Разбор обновился».
- **Уверенность:** высокая — по механике. Окно узкое.

### N4 (Low) — старый сверенный месяц выручки владелец исправить не может нигде
- **Где:** `lib/point-b/finmodel/revenue-history.ts:121–131` отказывает для любого месяца с `monthly_reconciliation` и пишет «исправить её можно там, на вкладке «План-факт»». Но форма «Факт за месяц» в UI предлагает только последний закончившийся месяц (`planfact/load.ts:88`, `reconciliation.period`).
- **Сценарий:** в сентябре владелец сверил август через форму. В ноябре он видит опечатку в августе. Таблица отвечает «исправьте в План-факте», а там только октябрь. Остаётся писать эксперту.
- **Подтверждено:** чтением кода. Уверенность высокая.
- **Предложение:** для месяцев старше последнего закончившегося — подсказка «напишите эксперту» или правка такого месяца в форме.

### Справочно (не дефекты)
