## 4. Новые проблемы, замеченные попутно

### Новые (в реестре нет)

**N5-1. Схему прода никто не сверяет с кодом, а main уже опережает прод. Предложенный приоритет — P2 (процесс), сейчас срочно.**

- **Факт.** Код main (`a2f33384`) требует миграций 155–157:
  - `crm_sync_acquire_lease` (`lib/crm/sync.ts:259`);
  - колонки синка и курсора;
  - крон `/api/cron/crm-sync` по расписанию `17,47 …` (`lib/cron/schedule.ts:54`).

  На проде применены только миграции по 154 (оркестратор).
- **Чего нет:**
  - `/api/health` не проверяет журнал `schema_migrations`: в `lib/` и `app/` нет ни одного обращения к нему;
  - в preflight `--since` необязателен: без него проверка миграций — только предупреждение (`scripts/deploy/preflight.mjs:562`);
  - журнал прода preflight не читает вовсе, сверяется только журнал staging;
  - защиты main нет (R-019).
- **Что сломается.** Срочный hotfix с main, выкачанный без бандла 155–157:
  - `/pulse` и API CRM отвечают 500;
  - `crm-sync` падает дважды в час;
  - сторож поднимает тревогу «падает».

  Откатить можно, но клиенту это видно.
- **Что сделать:**
  - в `/api/health` добавить проверку «последняя миграция из кода есть в журнале» (readiness, без деталей наружу);
  - в preflight для production сделать `--since` обязательным или читать журнал прода через `db-tools` (только чтение).

**N5-2. Клиент может сам поменять `profiles.email` через PostgREST. Предложенный приоритет — P2.**

- **Почему так.** Политика `profiles_update_own` (`supabase/migrations/001_onboarding_system.sql:280-284`) закрепляет только role и status. Триггер `profiles_guard_privileged_columns` (`140_staff_rls_from_staff_roles.sql:196-215`) защищает role, status, tier, feature_flags, approved_* и telegram_*, но не email. Колоночных грантов на `profiles` нет. Интерфейс сам почту в профиле не меняет: из браузера `profiles` только читается.
- **Как воспроизвести.** Любой вошедший пользователь отправляет `PATCH /rest/v1/profiles?id=eq.<свой id>` с `{"email":"<чужой адрес>"}`, используя публичный anon-ключ и свой JWT.
- **Что ломается:**
  - **Письма уходят на чужой адрес.** Напоминания и дайджесты адресуются по `profiles.email`: `lib/automation/data.ts:368`, `app/api/cron/crm-digest/route.ts:214-217`. Письма AIStart360 через Resend уйдут на чужой адрес. Это ещё и удар по репутации домена.
  - **Вход владельца в ГИГА.** Если клиент поставит почту владельца, `ilike('email', …).maybeSingle()` вернёт две строки и ошибку (`app/api/giga-admin/auth/route.ts:60`). Вход владельца по паролю в ГИГА отвечает 403. Обычный `/login` через GoTrue продолжает работать.
  - **Тексты для персонала.** В уведомления и карточки попадает не та почта.
- **Что сделать.** В том же триггере запретить менять `email` с ролей `authenticated` и `anon` (менять почту — только через GoTrue и сервер) плюс тест на БД. Это стоит сделать одной миграцией с R-053(в).

**N5-3. Новые кроны для клиентов не смотрят на режим техработ. Предложенный приоритет — P3.**

- `maintenanceSkipReason` вызывают только `reminders`, `client-digest` и `cron/agents`.
- Новые `crm-digest` (сводка CRM владельцу на почту, в WhatsApp и Telegram) и `billing-expiry` (письма «Pro заканчивается») его не вызывают.
- Если PO снова включит техработы, клиенты получат письма со ссылками в закрытый кабинет. Это тот же класс, что R-026.
- Сейчас техработы выключены (R-023), поэтому P3.
