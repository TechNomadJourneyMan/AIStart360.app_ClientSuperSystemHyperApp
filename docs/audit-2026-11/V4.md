## 1. Middleware: 2FA персонала (V3 пробелы a и b)

**Новый модуль `lib/mfa/factor-edge.ts`.** `secondFactorOnRecordEdge(userId)` определяет фактор по тем же правилам, что сервер и `staff_session_ok()` (143):
- источник — `user_security.totp_enabled` или любой passkey (`webauthn_credentials`);
- запрос: PostgREST через `edgeSupabaseFetch` с service-ключом, совместимо с Edge;
- ответ `null`, если прочитать не удалось или id не uuid; такой ответ не кэшируется;
- удачные ответы кэшируются на экземпляре на 15 с, не больше 500 записей.

**`middleware.ts`.** Общая функция `staffSecondFactorGate` + `staffMfaResponse` теперь применяется в трёх местах: ГИГА, `/super-expert` и общая проверка страниц. Для общей проверки условие — `profiles.role` ≠ `client`: admin, super_admin и expert (в том числе manager/analyst). Так покрыты вид персонала на `/dashboard` вместе с portfolio-gri, `/clients/*`, `/expert/*`, `/reports` и прочие страницы ADMIN_PATHS.

Правила проверки:
- есть step-up этой сессии → пропуск, в БД не обращаемся;
- фактор есть (флаги JWT, или запись в БД, если флагов нет) → `/2fa?from=…`. Это закрывает пробел (b): фактор добавлен уже после выдачи JWT;
- фактора нет, а `staff_require_mfa` включена → `/settings?tab=security&mfa=required`. Сам `/settings` из этой переадресации исключён, иначе была бы петля;
- состояние фактора прочитать не удалось → страница 503 «Временная ошибка», как при R-140 (fail closed).

Что работает как раньше:
- клиенты: только флаги JWT, лишних запросов нет;
- impersonation, dev-режим (`devModeOnForRequest`), публичные страницы и сам `/2fa`.

Чего не делал:
- пробел (c) из V3: dashboard по-прежнему читает токеном пользователя. Без step-up на страницу теперь не попасть, но перевод на service-role остаётся отдельной задачей;
- персонал с `profiles.role='client'` вне ГИГА/SE: правило фактора из БД к нему не применяется (staff-страниц вне ГИГА/SE у него нет), действует только прежняя проверка по флагам JWT.

**Тесты:**
- новые:
  - `tests/unit/auth/middleware-staff-mfa-pages.test.ts` — 20 кейсов, до правки падали 12;
  - `tests/unit/mfa/factor-edge.test.ts` — 7 кейсов;
- в 5 тестов middleware добавлен мок `secondFactorOnRecordEdge → false` («у этих аккаунтов фактора нет»): `integration/middleware`, `client-shell/middleware-cabinet-access`, `dev/dev-middleware`, `giga-crm/middleware-settings`, `giga-crm/super-expert-gate`. В тестовом окружении Supabase указывает на `127.0.0.1:1`, поэтому без мока срабатывал fail closed.

## 2. `/api/v1/action-plan`

- `GET ?userId=<чужой>` и `PATCH /[id]` для чужой задачи теперь проходят через `mayActOnUser`:
  - клиент — только своё;
  - эксперт — только назначенные клиенты;
  - персонал — по скоупу, после step-up этой сессии;
  - legacy `profiles.role` без `staff_roles` — 403.
- Отказ возвращается до ленивой генерации плана, то есть без записей.
- Вместо собственного `createClient` теперь `createServiceClient()`. В PATCH ошибка чтения отдаётся как `dbError`, а не 404.
- Тесты (`tests/unit/access/actor-scope-routes.test.ts`):
  - в таблицу 5 вызывающих добавлены два маршрута;

  - фейковый SDK-клиент теперь записывает операции записи в журнал.
- `point-b/action-plan-generation.test.ts`: добавлен мок `@/lib/supabase-service`. Сервисный клиент мемоизирован, и без мока тесты делили одну фейковую БД.
