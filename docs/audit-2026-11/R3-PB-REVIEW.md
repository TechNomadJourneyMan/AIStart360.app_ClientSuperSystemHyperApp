## High

### H1. ИИ-стратегия Точки Б (черновик для персонала) доступна клиенту на чтение и запись через RLS `point_b_analysis`
- **Где:** `supabase/migrations/029_point_b_analysis.sql:32-50` (политики `point_b_owner_read` FOR SELECT и
  `point_b_owner_write` FOR ALL для владельца диагностики); запись черновика —
  `app/api/v1/diagnostics/point-b/ai-generate/route.ts:100-121` (пишет `ai_strategy`/`ai_status` в ту же строку);
  147 добавляет только RESTRICTIVE-гейт оплаты на SELECT, т.е. Pro-клиент проходит.
- **Сценарий:** Pro-клиент берёт из браузера anon-ключ и свой JWT (они есть в браузере, supabase-js) и делает
  `GET {SUPABASE_URL}/rest/v1/point_b_analysis?select=ai_status,ai_strategy` — получает ИИ-стратегию, которую PO решил
  клиенту не показывать (новые черновики персонала через `ai-generate` и, вероятно, старые строки, сгенерированные
  для клиентов до R3). Дополнительно `point_b_owner_write` позволяет клиенту перезаписать `ai_strategy`/`ai_status`
  (и `roadmap`, `target_*`, которые читает `review/ai-draft` персонала) — подмена «ИИ-черновика» для персонала.
  Код R3 закрыл все API-пути (diagnostics/point-b, ai-status, PDF, share, чат), но не слой БД.
- **Подтверждено:** тест-БД 127.0.0.1:54329, одна транзакция с ROLLBACK
  (скрипт `<scratchpad>/pba_leak.sql`):
  Pro-клиент, `access_gates=true`, роль `authenticated` + JWT-claims →
  `SELECT ai_status, ai_strategy FROM point_b_analysis` вернул `completed | {"draft": "ИИ-черновик для персонала"}`;
  `UPDATE point_b_analysis SET ai_strategy=…` → `UPDATE 1`. `has_column_privilege('authenticated', …, 'ai_strategy', 'SELECT'/'UPDATE')` = t/t.
- **Предложение:** миграция 152+/153 (не пересекаться с SLA): `REVOKE SELECT (ai_strategy, ai_status), UPDATE ON point_b_analysis FROM authenticated`
  через column-grants, либо удалить `point_b_owner_read`/`point_b_owner_write` — все пути приложения уже читают/пишут
  сервисной ролью (diagnostics/point-b persist, ai-generate, чат перешёл на service). Решить с PO, обнулять ли старые
  `ai_strategy` клиентов. Добавить `point_b_analysis` в `tests/integration/db/point-b-rls.test.ts` (владелец не видит
  `ai_strategy`, не может UPDATE). Уверенность: высокая (технически); эксплуатация требует ручного REST-запроса.

## Medium

### M1. «Выручка по месяцам» после одобрения плана затирает/удаляет «Факт за месяц» сверки (в т.ч. введённый экспертом) и не пересчитывает план-факт
- **Где:** `lib/point-b/finmodel/revenue-history.ts:100-119` (upsert по `(company, period, 'revenue')` с
  `source='revenue_history', entered_role='owner'`; очистка удаляет строку «any source»);
  `app/api/v1/point-b/revenue-history/route.ts:75` (после сохранения нет `recomputeCompany`, в отличие от
  `saveFactsAndRefresh` в `lib/point-b/planfact/route.ts:98-107`). Таблица всегда редактируема
  (`components/point-b/RevenueHistorySection.tsx`, `FinmodelTab.tsx`), в т.ч. месяцы с меткой «факт сверки».
- **Сценарий:** план одобрен; эксперт ввёл выручку за прошлый месяц 7 млн («Факт за месяц», чекпойнт пересчитан).
  Владелец во «Финмодели» исправляет этот месяц на 1 млн → строка эксперта перезаписана (источник и роль сменились,
  след эксперта потерян), «Обзор» и прогноз уже на 1 млн, а «План-факт» продолжает показывать 7 млн до планового
  пересчёта (`DEFAULT_RECOMPUTE_CRON '0 22 * * 1,4'`, через Inngest). Очистка месяца удаляет факт эксперта целиком,
  чекпойнт всё ещё 7 млн. Нарушает «одна история для Обзора, пересчёта и план-факта».
- **Подтверждено:** временный тест на тест-БД в ROLLBACK
  (`<scratchpad>/vt/pb-revhist.scratch.test.ts`):
  после факта эксперта checkpoint=7000000/reconciliation; после правки владельца строка `{value 1000000, source revenue_history, entered_role owner}`,
  checkpoint (stored) = 7000000, `pb_runs`=0; после очистки строк 0, checkpoint 7000000.
- **Предложение:** при опубликованном плане — либо (а) месяцы с `source='monthly_reconciliation'` (и/или
  `entered_role='expert'`) только для чтения в таблице с подсказкой «исправьте через «Факт за месяц»», и очистка не
  трогает чужой источник; либо (б) после сохранения вызывать тот же `recomputeCompany(…, mode:'checkpoint', force:true)`
  и писать аудит. Добавить кейс в `point-b-mvp.test.ts`. Уверенность: высокая.

### M2. Чат (`get_point_b`) через сервисную роль открывает план владельца участникам компании и проверяет пейволл не того пользователя
- **Где:** `lib/chat/tools.ts:219-241`; доступ к инструменту — `toolsFor(canManage, sections)` по
  `resolveAccess(user.id)` вызывающего (`app/api/v1/ai/assistant/route.ts:97-128`), тенант — `can_read_company`.
- **Сценарий:** участник компании (не владелец, доступ `read`) спрашивает чат про Точку Б → получает одобренный план,
  сценарии, стратегию, проверенные рекомендации и авторасчёт владельца. По RLS `pb_plans`/`pb_plan_versions` — только
  владелец (сам RLS-тест это фиксирует), страница `/client/point-b` участнику этого не показывает; раньше инструмент
  отвечал участнику `no_access`. Пейволл: проверяется тариф участника, а не владельца (владелец Free + участник Pro →
  данные закрытого раздела уходят в чат).
- **Подтверждено:** чтением кода; комментарий в коде подтверждает намеренный обход («the plan tables are not readable
  by a member»). Уверенность: средняя — это может быть решением, но тогда оно расширяет модель доступа без PO.
- **Предложение:** отвечать только владельцу/персоналу (`t.userId === owner` или staff), иначе `no_access`; либо явно
  согласовать с PO и проверять `resolveFeature(owner, 'point_b')`.

### M3. Гри и умный ассистент по-прежнему считают Точку Б движком V2 — «один расчёт» не везде
- **Где:** `lib/assistant/context.ts:226` (`calculatePointBV2`) → `lib/assistant/mascot/insight.ts:56`

  и CAGR, которые модель не показывает и которые могут расходиться по цифрам. Требование 4 перечисляет «чат»; чат

- **Подтверждено:** чтением кода. Уверенность: высокая, что V2 используется; входит ли Гри в объём — решение PO.
- **Предложение:** кормить контекст ассистента из `loadPointBState`/`pointBReportFrom` (verdict, gap, forecast,
  missing), V2 оставить только как код.

### M4. Статус «waiting» обещает работу команды, но в этом коммите её никто не видит
- **Где:** `components/point-b/planPrep.ts:74-81` («План подготовит команда AIStart360 — мы пришлём уведомление…»;
  то же в `lib/point-b/report.ts:123`, `lib/reports/pdf.ts:657`, `app/r/[token]/page.tsx:673`);

- **Сценарий:** Pro-клиент с данными, но без черновика, читает «план подготовит команда», а у персонала нет ни списка,
  ни уведомления «клиент ждёт план» — план может не появиться никогда. Это ровно то, от чего требование 5 должно
  защищать (обещание работы без исполнителя).
- **Подтверждено:** grep по коду. Уверенность: средняя — закроется, если параллельный SLA-раунд подключит очередь
  «Pro без плана» до выката.
- **Предложение:** не выкатывать текст «waiting» без очереди/SLA или временно смягчить («Данных достаточно — передайте
  запрос эксперту» + кнопка/ссылка), а очередь подключить к `isWaitingForPlan`.

## Что проверено и в порядке

- **Миграция 151:** идемпотентна (`DROP CONSTRAINT IF EXISTS` + `ADD`; имя inline-CHECK из 132
  `pb_monthly_facts_source_check` — проверено на тест-БД), `lock_timeout`/`statement_timeout`, предусловие наличия
  таблицы, RLS не трогает. Откат: сначала перемаркирует `revenue_history → monthly_reconciliation` (данные не
  теряются), затем возвращает CHECK 132; порядок «сначала код» описан.
- **Одобрение (треб. 2):** `checkApprovalConditions` требует рассчитанные сценарии с известными ключами и темп из них;
  исключение снимает только условие цели. Единственный путь одобрения `approveVersionDetailed` (оба маршрута,
  включая legacy `review/point-b/approve`); переходы с проверкой статуса; `saveScenarios`/`updateDraft` только `status='draft'`.
- **Черновик в один клик:** только Admin/Super Admin (`approver`), скоуп клиента, `forbidTarget`, лимиты 6/10 мин и
  1/мин на компанию; без данных ничего не пишется; версия на одобрении → 409; заполненная стратегия не
  перезаписывается; рекомендации `pending_review` с дедупликацией; ничего не одобряет; ИИ без чисел не из данных
  (с оговоркой L10); без ключа — правила + предупреждение.
- **ИИ-стратегия (треб. 1) на уровне API:** `ai-generate` только персонал на чужом клиенте (свой вызов / без `user_id` /
  внутренний токен → 403 `staff_only`), fan-out и catch-up больше её не запускают, `ai-status` и `diagnostics/point-b`
  отдают `none/null`, вкладка «Подробности» и кнопка генерации убраны. (Слой БД — см. H1.)
- **Клиент видит только одобренное (треб. 6):** `loadPointBState` убирает сценарии из авторасчёта, стратегия/план-факт —
  только опубликованной версии, рекомендации — только проверенные (ожидающие только считаются), RLS подтверждён тестом.
- **Один расчёт (треб. 4):** PDF, «Поделиться», единый чат, вкладки ГИГА и эксперта — от `loadPointBState`/`pointBReportFrom`;
  «Подробности» не смонтированы, ссылка на план действий перенесена во «Стратегию». (Исключения — M3, L11.)
- **Выручка по месяцам (треб. 3):** 24 завершённых месяца, будущий/текущий месяц, повтор, отрицательные и >1e13
  отклоняются; только сессия (без IDOR), PUT «от имени» → 403, пейволл 402, лимит 20/час, 503 до миграции.
- **Числа:** история без двойного учёта (слияние по месяцу, сохранённые месяцы побеждают слой данных), деление
  `rescaled` годовых фактов на 12 сохранено; приоритеты план-факта (manual > сверка > факты) не изменены; цели в годовых
  единицах (`×12`) как раньше.
- **Пейволл и IDOR:** PDF — `gatePaidSection` + `resolveSubject` + `guardExpertClient`; share — `ownerSectionOpen`;
  revenue-history — `gateFeature`; ГИГА — `guardClientAccess`; эксперт — `guardExpertClient`.
- **Честные тексты (треб. 5):** «Эксперт готовит …» и «от вас ничего не требуется» убраны из клиентских вкладок, баннера,
  PDF, share и чата; состояния `in_work / in_review / waiting / needs_data` (оговорки M4, L13).
- **Регрессии:** приглашения от истории выручки не зависят; ежемесячная сверка работает (оговорка L1); пересчёт
  читает общую историю.
