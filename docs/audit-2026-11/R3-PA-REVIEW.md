## High

### H1. «Разбор готовится» может висеть навсегда, и выхода у клиента нет
- Где:
  - `app/api/v1/diagnostics/retry-ai/route.ts:61,83` — ставит `processing`, затем `fetch(...)` без таймаута, без `trackBackground`, без отметки о сбое (`.catch` только пишет в лог);
  - `lib/point-a/ai-review.ts:241` — `processing` показывается как есть, без проверки времени;
  - `components/point-a-v4/AiAnalysisCard.tsx:46,79` — кнопки «Повторить» при `processing` нет;
  - `hooks/usePointAState.ts:45` — опрос тяжёлого `/point-a/state` каждые 10 с, бесконечно;
  - `lib/point-a/snapshot.ts:389` против `:183` — строка получает `processing`, даже если вызов разбора не уйдёт (нет `baseUrl`).
- Сценарии:
  - (а) «Повторить» → внутренний `fetch` к ai-analyze падает на уровне сети (DNS / рестарт / недоступен) → строка навсегда в `processing`;
  - (б) деплой или перезапуск Railway (OOM на 8 ГБ) во время 1–2-минутного разбора на любом пути → никто не переводит строку в `failed` (фоновой «уборщицы» нет: в `app/api/cron/*` и `lib/functions/*` по `ai_status` ничего);
  - (в) не задан `NEXT_PUBLIC_APP_URL` → строка снимка в `processing`, а разбор не запускается.
  Клиент видит «Разбор готовится — обычно 1–2 минуты. Страница обновится сама», повторить не может. Выход — только следующий пересчёт с новой строкой.
- Подтверждено:
  - проба `probe-retry.test.ts`: при `fetch failed` записано только `[{"ai_status":"processing"}]`, ответ 200;
  - (б) и (в) — по коду, уверенность высокая. Как часто это случается на проде — средняя.
- Предложение:
  - запоминать время начала (`ai_generated_at := now()` при постановке `processing` либо новая колонка `ai_started_at`);
  - во view считать `processing` старше ~10 мин сбоем (`failed`, код `stale`) — тогда появится «Повторить»;
  - в retry-ai вызывать `fireAiFanOut` (таймаут, `markFailed`, `trackBackground`) вместо голого `fetch`;
  - в снимке ставить `processing`, только если `baseUrl` есть.

## Medium

### M1. «Повторить» можно использовать, чтобы жечь бюджет ИИ: нет проверки статуса и защиты от параллельных запусков
- Где:
  - `app/api/v1/diagnostics/retry-ai/route.ts:38–83` — статус строки не проверяется, перезапуск идёт для `processing` и `completed`;
  - `lib/point-a/analysis-cache.ts` — нет защиты от одновременных разборов одного входа;
  - `ai-analyze/route.ts` (`findCached` требует `ai_status='completed'`, а retry уже перевёл текущую строку в `processing`) — повтор готового разбора почти всегда генерирует его заново.
- Сценарий: владелец с платным доступом (или скрипт с его сессией) шлёт `POST /retry-ai` 10 раз в минуту.
  - Каждый вызов — новый полный разбор: 4 вызова модели, при сломанном ответе до 8, повтор уходит на тариф standard.
  - Все параллельные запуски проходят `assertAiBudget` до того, как расход записан, поэтому дневной бюджет перерасходуется на величину ~10 одновременных разборов.
  - UI это не провоцирует: кнопка есть только при `failed`. Но маршрут открыт.
- Подтверждено: проба `probe-retry.test.ts` — 5 вызовов для строки, уже стоящей в `processing`, дали 5 запусков ai-analyze.
- Предложение:
  - условное обновление `UPDATE … SET ai_status='processing' WHERE id=… AND ai_status IN ('failed','none')` (или `processing` старше N минут, см. H1); 0 строк → 409 «уже готовится» / «разбор готов»;
  - так же, как уже сделано в `catchUpPaidAi` (`diagnostic-row.ts:147`).

### M2. Миграция 150 падает на проде, если колонки уже существуют с данными
- Где: `supabase/migrations/150_point_a_ai_review.sql:74` (FK добавляется с проверкой) и `:100–107` (VALIDATE). Комментарий «validating is a scan that cannot fail» верен только для колонок, которые создала сама миграция.
- Сценарий: на проде колонки добавлены вручную. Миграция их пропускает, но проверки вешает и валидирует. Любое из условий ниже валит транзакцию целиком (`-1` → откат, прод цел, но выкатка заблокирована):
  - `ai_error` длиннее 500 символов (например, тело ответа провайдера);
  - `ai_reviewed_at` заполнено без `ai_reviewed_by_name`;
  - `ai_reviewed_by` указывает на несуществующий профиль.
- Подтверждено: `m150-probe.sh` на тест-БД:
  - чистая БД → OK;
  - `ai_error` TEXT 800 символов → `ERROR: check constraint "diagnostics_ai_error_len" … is violated`;
  - `ai_reviewed_at` без имени → `diagnostics_ai_review_complete … violated`;
  - «сирота» в `ai_reviewed_by` → FK violation;
  - `ai_generated_at` TEXT + `ai_error` VARCHAR(50) → OK.
- Предложение:
  - перед применением на проде проверить `information_schema.columns` и `max(length(ai_error))`;
  - в миграции валидировать только проверки на колонках, созданных в 150 (по маркеру `[150]`), и добавлять FK как `NOT VALID`;
  - иначе оставлять `NOT VALID` и писать об этом в лог.

### M3. Исправление B2 включило LLM-этапы конвейера на каждом автопересчёте, в том числе для Free
- Где: `lib/agents/definitions/diagnostics.ts:123` (в схему добавлен `'event'`), `lib/point-a/snapshot.ts:156,184`. В `lib/agents/*` и `lib/diagnostics/*` нет проверки платного доступа.
- Сценарий:
  - Раньше каждый автоматический запуск конвейера после снимка умирал на INVALID_INPUT.
  - Теперь каждая записанная Точка А по событию (автосохранение анкеты → очередь, ночной пересчёт, документ) ставит конвейер. В нём этапы «Гипотезы ИИ» (tier standard, до $0.4 за прогон) и «Рекомендации» (до $0.3).
  - Платность владельца не проверяется, этап запускается даже для предварительной оценки (`pipeline` не зависит от `preliminary`).
  - Требование 3 закрыто только для `point_a_hypothesis`. Гипотезы конвейера — тоже «ИИ-гипотезы», хотя их видит только персонал.
  - Добавляется и нагрузка на сервис `agents` (≤2 параллельно).
- Уверенность средняя: зависит от того, работает ли воркер агентов на проде, и от кеша по хешу входа.
- Предложение: решение PO. Варианты:
  - не ставить конвейер для `preliminary`;
  - гейтить LLM-этапы по `paidFanOutPaths(owner)`;
  - для Free оставить детерминированные этапы, а LLM-этапы помечать `skipped: free`.

### M4. Отметка «Проверено экспертом» и правки эксперта остаются на НОВОМ тексте ИИ
- Где: `app/api/v1/diagnostics/ai-analyze/route.ts:274–276`. Некешированная запись (полная и частичная) не очищает `ai_reviewed_at/_by/_by_name/ai_expert_edits`; `markFailed` их тоже не трогает.
- Сценарий: эксперт проверил разбор строки → «Повторить» или повторный разбор той же строки → клиент видит новый, никем не проверенный текст с отметкой «Проверено экспертом: Алия, 16.11» и чужим комментарием поверх. Для частичного разбора — то же самое.
- Сейчас это скрытый дефект: в коммите нет кода, который пишет `ai_reviewed_at`. Станет реальным, как только появится маршрут проверки разбора (над ним параллельно работает исполнитель SLA) — тогда это High.
- Подтверждено: проба `probe-ai-analyze.test.ts`:
  - после полной регенерации `{"status":"completed","draft":false,"review":{"by":"Алия"},"summary":"НОВЫЙ текст ИИ","note":"Сверил старый разбор"}`;
  - после частичной `{"status":"partial","draft":false}`.
- Предложение: в некешированной ветке (и при `partial`) писать `ai_reviewed_at/_by/_by_name/ai_expert_edits = null`; в кешированной без `cachedReview` — тоже null.

## Low

- **L1. Сбой не записывается, если запись диагностики падает не из-за отсутствия колонки.** `lib/point-a/ai-columns.ts:29` возвращает ошибку без записи одного статуса, поэтому `markFailed` (`ai-analyze/route.ts:321`) оставляет `processing`.
  - Пример: вручную созданная `ai_error VARCHAR(50)` → 22001 на длинном списке кодов.
  - Подтверждено пробой: ответ 502, `row ai_status = processing`. На пути веерного запуска (fan-out) это спасает `markFanOutFailed`, на пути retry — нет.
  - Предложение: при любой ошибке первой записи пробовать записать только статус.
- **L2. Гипотезы не догоняются после перехода на платный тариф.** `catchUpPaidAi` запускает только разбор. Гипотезы появятся лишь после изменения данных или ручного «Пересчитать» (ночной пересчёт без `force` вернёт «unchanged»).
  - Предложение: в catch-up вызывать `addHypotheses` для последнего снимка.
- **L3. PDF и ссылка показывают частичный или предыдущий разбор без пометки «частично» / «последняя попытка не удалась».** `export/report/route.ts:324`, `share/report-data.ts:299` — `aiNote` говорит только «черновик».
  - Предложение: добавлять в `aiNote` текст `aiFailureText` при статусе `partial`/`failed`.
- **L4. Ответ `/api/v1/point-a/state` отдаёт клиенту `errorCode` и `model`.** `ai-review.ts:255`; UI показывает их только персоналу. Это только коды, данных клиента нет, но при желании можно вырезать их для не-персонала на сервере.
- **L5. Расхождения «Минимума для Точки А» с официальным правилом в крайних случаях.**
  - `score-path.ts` не учитывает требование движка «хотя бы один блок на фактах» (`engine.ts`, `factual`): если балл есть только у гипотез, подтверждённых экспертом, карточка скажет «данных хватает», а балла не будет.
  - `surveySent` выводится из `snapshot.assessment` (`state.ts:391`): v1-снимок считается «отправленным»; после отправки с упавшим пересчётом карточка снова предложит «отправить анкету».
  - Остальное (≥60 % веса, «Финансы»/«Продажи», 40 % на блок) совпадает с `overallAllowed` / `scoreBlock`.
- **L6. Текст «эксперт проверит» обещает проверку, которой пока нет.** Пока не выкачены задача и маршрут проверки эксперта, проверять некому. Выкатывать R3-PA вместе с ними.
- **L7. Качество тестов.**
  - Поведенческие и хорошие: ai-analyze-r3pa (фейковая БД), state-r3pa, r3pa-ui (рендер), интеграционный тест миграции 150 на реальной схеме.
  - Проверяют исходный текст, а не поведение: часть r3pa-wizard (`readFileSync` + regex по page.tsx) и ai-note-share-pdf.
  - Не покрыты: миграция при уже существующих колонках с данными (M2), повтор при `processing`/`completed` (M1), очистка отметки проверки (M4), застрявший `processing` (H1).
- **L8. Справочно, вне диффа.**
  - Публичная ссылка `/r/[token]` продолжает показывать платную Точку А после перехода владельца на Free (гейт есть только при создании). Это было и раньше; теперь кнопка «Поделиться» прямо на странице.
  - Персонал может создать ссылку для Free-клиента — осознанное действие персонала.

## Проверено и в порядке

1. **Конвейер (B2).** `pipelineTriggerOf` переводит `'event'/'expert'/'schedule'` в значения, которые принимают orchestrator (zod), `session.open` и CHECK-ограничения `agent_tasks`/`diagnostic_sessions` (085/086). Интеграционный тест «event opens a session» зелёный. Изнутри конвейера (`fromPipeline`) конвейер повторно не запускается. Оговорка про стоимость — M3.
2. **GRI 0–10.** `state.ts` → `toGri` (`lib/format/gri.ts`), `GriCard` показывает «из 10», giga-панель тоже. Ссылок на `index100` не осталось.
3. **Гипотезы и Free.** `afterWritePlan.hypotheses` требует путь ai-analyze в `paidPaths`. В рабочем окружении `paidAi` задан всегда, при ошибке возвращается `[]` (закрыто). `addHypotheses` — единственный путь генерации. Оговорки — M3 и L2.
4. **Причина сбоя ИИ-разбора.** Пишутся `ai_error` (код части, без тела ответа), `ai_model`, `ai_generated_at`. Сбой отвечает 502, а не 200. Частичный разбор (≥3/4) сохраняется с `partial` и статусом `failed`, без хеша кеша — кеш его никогда не переиспользует. Ключ `partial` принадлежит самому разбору и выбрасывается при полном разборе. До миграции 150 код откатывается на запись одного статуса (PGRST204/42703).
5. **Страница.** «Черновик ИИ — эксперт проверит»; статусы готовится / не удался / частично. «Повторить» показан владельцу и персоналу, сервер повторно проверяет `mayActOnUser` и пейволл. Разбор скрыт, если официального балла нет. Free получает только `expressPointASlice` (без `aiAnalysis`, `scorePath.needs` пустые).
6. **PDF и «Поделиться».** Кнопки видны только при официальном балле, владельцу и персоналу. Пейволл в маршрутах `export/report` и `share` (402 для Free) сохранён. PDF и ссылка читают тот же `aiAnalysisView` (`select *`) с пометкой черновика. IDOR не найден: `diagnostics` читается сессией под RLS (147), retry-ai проверяет владельца через `mayActOnUser`.

   - `score-path` = правило `overallAllowed` (60 % веса + «Финансы»/«Продажи»; блок получает балл при 40 % данных).

   - Путь v1 для компании удалён. Строка без компании пишется `preliminary` (без баллов), сторонних записей `calculatePointA` нет.
