## 1. Middleware (главная линия)

**Какие страницы закрыты.** Список задаёт `lib/impersonation/account-pages.ts` → `isAccountSecurityPage(pathname, searchParams)`:
- `/auth/reset-password` (и подпути, с любыми параметрами). Это единственное место в браузерном коде, где вызывается `supabase.auth.updateUser`. Grep по `updateUser(`, `resetPasswordForEmail`, `reauthenticate`, `auth.mfa`, `mfa.enroll/challenge/verify/unenroll` в `app`, `components`, `lib`, `stores`, `hooks` других вызовов из браузера не нашёл. Второй `updateUser` стоит в серверном `app/api/v1/settings/password`, и его уже закрывает `refuseDuringImpersonation`.
- `/2fa`. Это step-up клиента и расход его резервных кодов. Кроме того, кнопка «Выйти» на странице делает global `signOut()`.
- `/settings?tab=security`, включая `&mfa=required`, повтор `tab` и любой регистр. Остальные вкладки настроек открываются.
- Смены e-mail в приложении нет: `settings/profile` e-mail не меняет, это подтверждено и в Z2. `/forgot-password` закрывать не нужно: вошедшего пользователя middleware и так уводит со страниц входа. Письмо в любом случае уходит на почту клиента.

**Как определяется impersonation.** Так же, как во всём middleware (R-008): подлинный cookie того же пользователя, привязанный к этой сессии GoTrue (`asid`), при открытой записи `impersonation_sessions`. Сессия без cookie, но с серверной привязкой, как и раньше, сразу завершается (`scope:'local'`). Проверка стоит сразу после установки `impersonating = true` и действует в режимах просмотра и правки.

**Ответ.** Редирект на `/client/home?unavailable=impersonation`. На главной кабинета (`components/user-dashboard/UserHome.tsx`, `UnavailableNotice`) показывается: **«Недоступно в режиме просмотра от имени клиента»** и пояснение, что пароль, 2FA, ключи и сеансы клиента меняет только сам клиент. Сама сессия impersonation не завершается. Попытка пишется в `admin_audit_log`: `action = 'impersonation.account_page_blocked'`, `entity_type = 'page'`, sid, администратор, клиент, IP, UA. Для этого `auditImpersonatedRequestEdge` получил необязательные `action`/`entityType`, значения по умолчанию прежние.

**Fail closed:**
- Привязку сессии не удалось прочитать (`boundImpersonationEdge → 'unknown'`) → на этих страницах ответ 503 «Временная ошибка» с автообновлением. Остальные страницы работают как раньше.
- Профиль не читается (R-140): раньше `/auth/reset-password` в этом случае отдавалась как «публичная» ещё **до** проверки impersonation. Теперь страницы учётной записи из «публичных» в этой ветке исключены → 503.

## 2. Вторая линия (UI)

- `app/auth/reset-password/page.tsx` стал серверной обёрткой. Форма перенесена без изменений поведения в `app/auth/reset-password/ResetPasswordForm.tsx`. Обёртка через `accountLockForThisSession(userId)` (`lib/impersonation/account-lock.ts`, поверх `impersonationOfThisSession` из Z2) для сессии impersonation **не рендерит форму**: компонент с `updateUser` не попадает на страницу, остаётся только пояснение. «Не удалось проверить» → тоже без формы, с текстом «Не удалось проверить режим сессии…». Гость и обычная сессия получают форму как раньше. Hash-ссылки восстановления по-прежнему работают: до входа сессии нет, проверка даёт «none».
- Настройки: `app/(dashboard)/settings/page.tsx` параллельно с профилем вычисляет `accountLock` и передаёт его в `SettingsClient`. Переключение вкладки происходит на клиенте, мимо middleware, поэтому новый `SecurityTabContent` вместо `SecurityPanel` (пароль, 2FA, ключи, сеансы, события) показывает `components/impersonation/AccountLockedNotice.tsx`. Ни одной кнопки, ни одного запроса. Сами API уже отказывают с 403 (guard из Z2).
- Не менял `app/2fa/page.tsx` (global `signOut()` в «Выйти»). В impersonation страница теперь недостижима (п.1). При желании её можно перевести на `signOutThisBrowser()` из SR-06 — это одна строка.

## 3. `impersonate.view` только для super_admin/admin — НЕ включено, ждёт PO

Матрица прав задаётся **только в коде**: `lib/admin/rbac.ts`, `ROLE_PERMISSIONS`. В миграциях зеркала нет, поэтому миграция не нужна. Сейчас право есть у `crm_manager` (view+edit), `super_expert` (view+edit) и `support` (view). Точная правка — три строки в одном файле:

```diff

   ...
-  'impersonate.view', 'impersonate.edit',
   'inbox.view', 'inbox.manage', ...
 ]
   super_expert: new Set<Permission>([
     ...
-    'impersonate.view', 'impersonate.edit',
     'inbox.view', 'leads.view',
   support: new Set<Permission>([
     'dashboard.view', 'users.view', 'users.sensitive', 'survey.view', 'gri.view', 'activity.view', 'cjm.view',
-    'impersonate.view', 'inbox.view', 'leads.view',
+    'inbox.view', 'leads.view',
```

Это право проверяют `canImpersonate`, `POST/GET /api/giga-admin/impersonation`, `[id]/end`, пункт меню «Вход от имени» (`lib/admin/nav.ts`) и страница `/admin-giga-panel/impersonation`. Всё это отключится само. Вместе с правкой нужно поправить тесты, где закреплено прежнее: `tests/unit/giga-crm/rbac-journey.test.ts:24` (support → false) и `tests/unit/giga-crm/super-expert.test.ts:68` (убрать `impersonate.*` из ожидаемых прав SuperExpert). Нужно также обновить комментарий в `rbac.ts` про SuperExpert («может открыть кабинет клиента»). Промежуточный вариант без кода: выключить в настройках платформы тумблер `super_expert_impersonation`. Он закрывает только super_expert, support и crm_manager остаются.

## 4. Взаимосвязь с V3 (прямой GoTrue/PostgREST)

Мои правки закрывают **страницы портала**. Токен сессии impersonation по-прежнему лежит в JS-доступном cookie. Сотрудник может сам вызвать `PUT /auth/v1/user {password}` или `/auth/v1/factors` (anon key публичен), а также писать в PostgREST в обход режима просмотра. В коде приложения это не закрыть. Что нужно сделать на стороне V3:
- короткий срок сессии impersonation и её серверный отзыв (`admin.signOut(jwt,'local')`) по окончании и по крону на `expires_at`; JWT expiry ≤ 15 мин;
- RESTRICTIVE-политики записи `NOT is_impersonation_session()` по индексированной таблице привязок. Сейчас привязка лежит в `admin_audit_log`; от неё же зависит и мой fail-closed по `'unknown'`;
- Auth Hook или «Secure password change» GoTrue, который отклоняет смену пароля и факторов для `session_id`, привязанного к impersonation.

Пока этого нет, единственная мера против прямого вызова — п.3, сужение круга сотрудников с `impersonate.view`. SEC-REVIEW-2 §3 п.2(г) считает её обязательной до запуска.
