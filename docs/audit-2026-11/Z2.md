## SR-04 — захват аккаунта до его создания

**Было:** `acceptInvitation(email, userId)` брала самое свежее приглашение по e-mail и выдавала `staff_roles` любому аккаунту с этим адресом.

**Стало** (`lib/admin/invites.ts`, `app/auth/verify/route.ts`):
- `sendPlatformInvite` создаёт токен (32 случайных байта, base64url), кладёт в ссылку `/auth/verify?...&invite=<токен>`, в `platform_invitations.metadata.accept_token_hash` — только SHA-256. Для `type=invite` записывается `user_id`, созданный самим `generateLink` (по нему «новый» аккаунт отличается от существовавшего). Приглашение сотрудника без сохранённой записи не отправляется (письмо без пути к роли).
- `/auth/verify` вызывает `acceptInvitation({ inviteToken, userId, email, accessToken })` **только при наличии `invite=`**. Совпадение e-mail без токена роль не даёт никогда.
- `acceptInvitation`: поиск по хешу токена → e-mail записи = подтверждённый адрес ссылки → статус `sent` → не просрочено → **атомарный захват** (`update … where status='sent'`, второй клик/гонка роли не получают).
- Если в приглашении есть роль и аккаунт «существовал» (не создан этим приглашением, или `created_at < sent_at`, или `email_confirmed_at` пуст, или аккаунт не читается) — **до выдачи роли**: случайный пароль (`admin.updateUserById`), отзыв всех остальных сессий (`admin.signOut(jwt ссылки, 'others')` — сессия владельца почты, только что созданная ссылкой, остаётся), удаление факторов 2FA (`adminResetUserMfa` + штатные факторы GoTrue `admin.mfa`), отзыв MCP-токенов, OAuth-токенов, `staff_telegram_links`, `profiles.telegram_chat_id/link_code`; событие `security.invite_account_secured` (activity_log, category security, critical). Затем владелец отправляется на `/auth/reset-password` задать пароль.
- Любой шаг упал (или нет сессии ссылки) → роль **не выдаётся**, запись `failed` (`secure_failed: …`), событие `security.invite_accept_refused`.

**Остаточные риски / рекомендации PO:**
1. **Обязательное подтверждение e-mail при регистрации** (`app/api/auth/register/route.ts`, `email_confirm: true`) — не включал по заданию. Рекомендую: это закрывает весь класс pre-account takeover (не только приглашения), например через `signUp` с письмом или `email_confirm:false` + письмо подтверждения; автоодобрение — только после подтверждения.
2. Access-JWT атакующего (до `exp`, по умолчанию ≤1 ч) после отзыва сессий остаётся годен для **прямого PostgREST**, а роль выдана сразу → в этом окне он получит RLS-права сотрудника (через приложение — нет: `getUser()` в GoTrue проверяет существование сессии). Закрывается на стороне БД вместе с SR-01: в `current_staff_role()`/`is_active_expert()` требовать `EXISTS (SELECT 1 FROM auth.sessions WHERE id = (auth.jwt()->>'session_id')::uuid)` (и `aal2`). Альтернатива — откладывать выдачу роли до установки нового пароля.
3. Старые приглашения (отправленные до выката) токена не имеют → роль по ним не выдастся; нужно переотправить из панели.
4. `scripts/invite-staff.ts --grant-now` по-прежнему выдаёт роль существующему аккаунту по e-mail (осознанное действие оператора). Рекомендация: убрать флаг или выдавать роль только аккаунтам с подтверждённой почтой.
5. Данные, оставленные прежним держателем в аккаунте (профиль, компания, документы), остаются у владельца почты — стоит показать ему уведомление.

## SR-06 — global signOut во время impersonation

- Новый `POST /api/v1/auth/sign-out` (манифест: `session`): сервер решает по cookie impersonation **и** по серверной привязке сессии GoTrue (R-008). Impersonation или «не удалось выяснить» → `endImpersonationInThisBrowser` (`scope:'local'`, закрытие `impersonation_sessions`, аудит `impersonation.ended`), ответ ведёт в карточку клиента; обычный клиент → `signOut()` global, как раньше. Путь добавлен в `VIEW_MODE_ALLOWED_API` (работает и в режиме просмотра).
- Логика выхода вынесена из `app/api/v1/impersonation/exit` в `lib/impersonation/exit.ts` (поведение exit не изменилось; тесты R-008 зелёные).
- `DELETE /api/giga-admin/auth`: во время impersonation — только local + закрытие записи, иначе как раньше.
- Браузер: `lib/auth/sign-out-client.ts` `signOutThisBrowser()` — спрашивает сервер, сам делает только `scope:'local'` (и при недоступности сервера). Подключено в `ClientNav`, `GigaSidebar` (`scope:'local'` после серверного DELETE), `waiting-room`, `ClientPointALegacy`, `stores/auth.store.ts` (`logout` — Header/Sidebar/ExpertHeader/ExpertSidebar старого кабинета). Не трогал `app/2fa` и `app/super-expert/login` — там impersonation не бывает (middleware пропускает 2FA при impersonation).
- В `tests/contracts/route-auth-matrix.test.ts` в признаки `session` добавлен `endImpersonationInThisBrowser(` (exit-маршрут теперь вызывает его).

## SR-07 — чувствительные действия из impersonation

`lib/impersonation/guard.ts`: `impersonationOfThisSession()` (cookie того же пользователя — даже просроченный; либо привязка сессии GoTrue — работает без cookie; ошибка чтения → `unknown`) и `refuseDuringImpersonation()` → 403 `{ error: 'Недоступно в режиме просмотра от имени клиента', code: 'IMPERSONATION_FORBIDDEN' }`, `unknown` → 503 (fail closed), событие `security.impersonation_action_blocked` в журнал безопасности клиента. Действует и в режиме правки.

Где стоит:
- `guardFactorChange` (`lib/mfa/factor-guard.ts`) — до любых проверок, включая **первый фактор**: 2fa/setup, 2fa/verify, 2fa/disable, backup-codes/regenerate, webauthn register options/verify, webauthn/credentials DELETE.
- Явно: `2fa/challenge` (расход резервных кодов, выпуск step-up), `webauthn/authenticate/options|verify`.
- `settings/password` (смена пароля), `settings/sessions/revoke-all`, `settings/telegram` POST/DELETE (привязка канала), `consents` PUT (юридические согласия клиента), `reports/[id]/link` POST (долгоживущая ссылка на отчёт).
- Уже были закрыты: `mcp/tokens` POST (canCreate), OAuth-согласие (impersonation только клиентов, MCP — только персонал), смена e-mail в приложении отсутствует (`settings/profile` e-mail не меняет).

**Для Z1:** добавить `refuseDuringImpersonation(req, user, 'share.create')` в `app/api/share/**` (создание/продление share-ссылок) — те же основания, что для `reports/[id]/link`.

**Обход прямыми вызовами (SR-07b) — в коде приложения не закрыть.** Access-токен сессии impersonation лежит в JS-доступном cookie; `PUT /auth/v1/user {password}`, `/auth/v1/factors`, запись в PostgREST идут мимо Next. Особенно: страница `/auth/reset-password` меняет пароль любой живой сессией без текущего пароля, а «Secure password change» GoTrue требует повторной аутентификации только для сессий старше 24 ч — свежая сессия impersonation её не требует. Варианты (по убыванию надёжности):
1. **Не выдавать сессию GoTrue вовсе**: impersonation как серверный прокси — браузер получает только наш подписанный httpOnly cookie, все чтения идут через серверные маршруты service-role со скоупом «от имени uid» (режим просмотра). Самое надёжное, но большая переделка.
2. **Отдельный короткоживущий JWT с ограниченной ролью**: подписывать собственный JWT (секрет проекта) с `role='impersonation_view'`, `sub=<клиент>`, `exp` 15–30 мин, claim `imp_sid`; Postgres-роль `impersonation_view` с GRANT только SELECT и RLS-политиками на чтение; в GoTrue такой токен не годится для `/user`/`/factors` (нет сессии) → смена пароля/факторов невозможна. Хранить в httpOnly cookie, отдавать в браузер через серверные маршруты.
3. **RLS-запрет записи из impersonation**: RESTRICTIVE-политики `USING/WITH CHECK (NOT public.is_impersonation_session())`, где функция смотрит `auth.jwt()->>'session_id'` в таблице привязок (сейчас привязка в `admin_audit_log`; нужна отдельная индексированная таблица `impersonation_auth_sessions`). Закрывает PostgREST, но не GoTrue.
4. **Минимум сразу:** отзыв сессии impersonation по окончании и по таймеру на сервере (`admin.signOut(jwt,'local')` из крон-задачи по `expires_at`, сейчас сессия живёт до своего refresh-срока), `JWT expiry` проекта ≤ 15 мин, httpOnly для auth-cookie сессии impersonation (с @supabase/ssr — только при серверном рендеринге без браузерного клиента), включить «Secure password change» и «Secure email change» в GoTrue, хук GoTrue «password verification / MFA verification» (Auth Hooks) отклоняет запросы, чей `session_id` привязан к impersonation.
