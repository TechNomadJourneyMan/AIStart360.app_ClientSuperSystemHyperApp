# ТЗ: полноценная Точка А

Дата: 2026-10-12 · Статус: согласовано с PO, ожидает ревью текста · Ветка: `claude/tz-clarifying-questions-680502`

## 0. Цель и принципы

Точка А — это автоматически собранная, проверяемая картина текущего состояния бизнеса. Она строится из анкеты, загруженных документов (парсер/OCR), метрик и целей клиента. По ней моделируется Точка Б и строится план перехода А→Б.

Принципы:

1. **Анкета главная.** В ней задаются метрики. Документы и метрики дополняют анкету и заполняют пустые периоды.
2. **Всё привязано к периоду.** Значение без периода считается значением текущего периода. Сравнивать можно только значения за один и тот же период.
3. **У каждой цифры есть происхождение.** Источник, период, достоверность, тип: FACT / CALCULATED / INFERRED / AI_HYPOTHESIS.
4. **Расчёт один, его результат читают все.** Страница, NBA, AI-анализ, Точка Б и чат читают один сохранённый снимок.
5. **Пересчёт событийный и инкрементальный.** Любое изменение данных обновляет Точку А. Пересчитывается только то, что затронуто, и результат сливается с предыдущим снимком.
6. **Клиент видит результат сразу.** Эксперт дополняет его, но не блокирует.
7. **Пустые места честно показываются как пустые.** Где данных нет, пишем «данных не хватает». AI-оценка допустима только с пометкой «гипотеза».

### Текущее состояние (кратко)

- **Две страницы:** `app/client/point-a/page.tsx` и `app/(dashboard)/point-a/page.tsx`. Вторая читает диагностику по `calculated_at`, а не по `is_current`.
- **Балл считается в разных местах по-разному.** Движок — `lib/point-a-engine.ts:721` `calculatePointA`. AI-анализ (`diagnostics/ai-analyze/route.ts:154`), NBA (`api/v1/nba/route.ts:128`) и старая Точка Б (`api/clients/[id]/analysis/point-b/route.ts:38`) вызывают его без `resolvedInputs`, то есть считают другой балл.
- **Выбор значения метрики не учитывает период.** `lib/metrics/company-metrics.ts` берёт самую свежую строку. Расхождения между источниками не ищутся. Есть только `alternatives` в `lib/documents/extraction.ts`.
- **Событие `METRIC_UPDATED` объявлено, но никем не отправляется.**
- **Цели фактически только по выручке.** `companies.target_revenue_*` есть, а `metric_targets` UI не использует. `GoalsBar` ничего не сохраняет.
- **Два чата:** «Гри» (`/assistant/converse`, история только в браузере) и report-chat (`/api/v1/ai/chat`, RAG). Ни у одного нет стриминга и инструментов.
- **Мёртвый код:**
  - `lib/point-a/scoring-v2.ts`, `weights.ts`;
  - маршруты `point-a/{narrative,history,benchmarks,v3}`;
  - `GRIAssessmentTrendChart.tsx`;
  - `lib/point-b-engine.ts` (v1).

## 1. Слой данных: факты с учётом периодов

### 1.1 Модель факта

Единое хранилище фактов — `public.metrics` + `public.metric_value_history`. Колонки периода и `provenance` у них уже есть (миграции 085, 102). Факт описывается так:

```
(company_id, metric_key, period_year, period_quarter?, period_month?, scenario='actual',
 value, unit, currency, source_kind, source_ref, confidence 0..1, provenance jsonb)
```

`source_kind` принимает значения: `survey | document | manual | integration | formula | ai_estimate`. Для `source_kind = survey` в `source_ref` хранится ключ ответа, для `document` — `document_id` + страница/поле.

### 1.2 Адаптер «анкета → факты»

Новый модуль `lib/data-layer/survey-facts.ts`.

- **Реестр соответствий** `SURVEY_FACT_MAP`: ключ анкеты → `{metric_key, period, unit, transform}`. Реестр лежит в одном файле и покрыт тестами.
  - Год из ключа: `s9n_revenue_2024` → 2024, `s2_revenue_2025` → 2025.
  - Относительные периоды: `s9n_change_vs_2023` → производный факт (прирост).
  - Ключи без периода («текущая ситуация») → текущий период. Год берётся из `answered_at`; если показатель месячный — ещё и месяц.
  - Таблица `s8n_metrics_table` → по строке на метрику и период.
- **Когда запускается:** при каждом сохранении ответа анкеты (upsert) и при завершении анкеты.
- **Удаление ответа** отзывает факт: строка удаляется, событие пишется в историю.

### 1.3 Нормализация и смарт-фильтрация

Модуль `lib/data-layer/normalize.ts`. Это чистые функции, всё покрыто юнит-тестами.

- **Числа:** парсинг «14 млн», «14,5 млн ₸», «$1.2M», «1 200 000». Валюта по умолчанию — валюта компании (KZT). Пересчёт по курсу на дату периода, курс хранится в provenance.
- **Масштабирование потоков:** месяц ↔ квартал ↔ год. Используется уже существующая логика `source-adapters.ts`, она выносится в общий модуль. Факт о масштабировании пишется в provenance.
- **Валидация диапазонов** по каталогу метрик: маржа от −100% до 100%, конверсия от 0 до 100%, нет отрицательной выручки и т.п. Значение вне диапазона сохраняется как `rejected` и попадает в расхождения с типом `invalid`.
- **Аномалии:** если значение отклоняется от собственной истории метрики более чем в 3 раза (или robust z-score > 3.5 при ≥4 точках), ставится флаг `anomaly`. Расчёт он не блокирует, но снижает confidence.
- **Дубли:** одинаковые значения (в пределах 0.5%) за один период из разных источников схлопываются в один факт с несколькими `source_ref`. Это подтверждение, и confidence растёт.
- **Свежесть:** confidence затухает с возрастом данных. Для текущей ситуации — после 6 месяцев без обновления, для исторических периодов затухания нет. Порог задаётся в реестре настроек.

### 1.4 Выбор значения (resolver) с учётом периода

`lib/metrics/company-metrics.ts` и `resolver.ts` выбирают значение по паре `(metric_key, period)`.

Приоритет внутри одного периода:

1. ручная правка эксперта или клиента, сделанная при закрытии расхождения;
2. анкета;
3. документ;
4. интеграция;
5. формула;
6. AI-оценка.

Это соответствует решению PO «анкета главная». Нынешний `SOURCE_RANK` меняется соответственно, а старая логика «побеждает самый свежий» убирается.

«Текущее значение» метрики — это значение за последний период, по которому есть данные, с явной меткой этого периода. Например, «Выручка: 14 млн ₸ · 2024 · документ».

### 1.5 Сверка (reconciliation)

Модуль `lib/data-layer/reconcile.ts`, таблица `public.data_discrepancies`:

```
id, company_id, metric_key, period_key ('2024' | '2025-Q2' | '2025-09'),
kind ('conflict' | 'invalid' | 'anomaly' | 'missing_period'),
candidates jsonb  -- [{value, unit, source_kind, source_ref, confidence}]
chosen_value, status ('open' | 'resolved_user' | 'resolved_expert' | 'ignored' | 'auto_resolved'),
resolved_by, resolution_note, created_at, resolved_at
UNIQUE (company_id, metric_key, period_key, kind) WHERE status = 'open'
```

- **Порог конфликта:** расхождение больше 5% (настраивается для каждой метрики в каталоге) между источниками за один и тот же период.
- **Значения за разные периоды конфликтом не считаются.** Например, «анкета — текущий 2025, документ — 2024» не конфликт, а два факта на шкале времени.
- **Пока конфликт открыт,** в расчёте используется значение по приоритету из §1.4. Его confidence снижается на 0.3, и блок показывает бейдж.
- **Автозакрытие:** если новое значение устраняет конфликт, запись получает статус `auto_resolved`.
- **RLS:** клиент видит свои расхождения, эксперт — расхождения назначенных ему клиентов, админ — все.

### 1.6 События

- Отправлять `METRIC_UPDATED` при любой записи в `metrics`: ручной, из интеграции или из адаптера анкеты. Сейчас событие объявлено, но не отправляется.
- Новые события: `SURVEY_ANSWER_CHANGED`, `DOCUMENT_DELETED`, `DISCREPANCY_RESOLVED`, `TARGET_CHANGED`, `BLOCK_CONFIG_CHANGED`, `POINT_A_UPDATED`. Они добавляются в `lib/events/platform-names.ts`.
- **Удаление документа** отзывает все факты с этим `source_ref`, пересчитывает сверку и запускает пересчёт Точки А.

## 2. Движок Точки А

### 2.1 Единый вход

Новая функция `buildPointASnapshot(companyId, changeSet?)` в `lib/point-a/snapshot.ts`.

- **Порядок работы:** читает факты через resolver (§1.4), применяет конфигурацию блоков (§2.2), считает баллы и пишет снимок.
- **Внутри** используется переработанный `calculatePointA`. Вход у него — не `answers`, а `ResolvedFacts`. Совместимость сохраняется адаптером, пока не мигрированы все места вызова.
- **Все потребители читают снимок** (`diagnostic_sessions.overview` + текущая строка `diagnostics`), а не считают балл сами. Это AI-анализ, NBA, Точка Б, `/client/home`, чат, письма и боты.

### 2.2 Конструктор блоков

Таблицы:

- `pa_block_library` — блоки: `key`, название, описание, иконка, список метрик и правил оценки. Правила — пороги по метрикам, вес метрики внутри блока, направление.
- `pa_templates` — отраслевые шаблоны: набор блоков, веса, привязка к отраслям и стадиям. Шаблон `default` содержит 7 блоков: финансы 0.25, продажи 0.20, операции 0.15, маркетинг 0.12, стратегия 0.10, команда 0.10, продукт 0.08.
- `pa_company_config` — настройка для компании: `template_key`, переопределения эксперта `{block_key: {weight, enabled}}`, вид клиента `{hidden: [], order: []}`, `version`.

Права:

| Уровень | Что может | Где |
|---|---|---|
| Админ | Библиотека блоков и метрик, шаблоны, правила оценки | GIGA-CRM → «Точка А: конструктор» |
| Эксперт | Шаблон клиента, добавить или выключить блок, изменить веса (сумма нормируется до 1) | Карточка клиента (User 360) |
| Клиент | Скрыть, вернуть, переставить, добавить блок из библиотеки | Страница Точки А, режим «Настроить» |

**Защита от «накрутки»:** блок, который скрыл клиент, пропадает только из вида, а в итоговом балле участвует. Блок, который добавил клиент, получает вес из шаблона, а если в шаблоне его нет — вес 0, и он отображается как «информационный». Веса меняет только эксперт или админ.

**Автовыбор шаблона:** по `companies.industry` и стадии бизнеса. Если подходящего шаблона нет, берётся `default`.

### 2.3 Расчёт балла и достоверности

- **Балл блока** — взвешенная сумма оценок метрик блока (0–100) по правилам из библиотеки.
- **Достоверность блока** — среднее confidence использованных фактов × доля покрытия метрик блока.
- **Нехватка данных в блоке:**
  - покрытие < 40% и нет косвенных данных → статус `insufficient_data`, балл не показывается, текст «Данных не хватает» и список того, что загрузить;
  - покрытие < 40%, но косвенные данные есть → AI-оценка с типом `AI_HYPOTHESIS`, бейджем «гипотеза» и confidence ≤ 0.4;
  - ни один из этих баллов в итог не превращается в FACT.
- **Итоговый балл** — сумма весов × баллов по блокам с данными, нормированная на сумму их весов. Рядом показывается общая достоверность и количество блоков без данных. Тихой подстановки нуля нет: это устраняет класс багов COR-01.
- **Стадия** (seed/early/growth/scale) и `health_index` сохраняются. Расчёт стадии переносится на факты.
- **Сильные стороны** — блоки и метрики с наивысшим результатом при достоверности ≥ 0.6. Сейчас они считаются по полноте данных (`helpers.ts:176-196`), это исправляется.
- **Чек-лист «Что загрузить»** ранжируется по ожидаемому приросту достоверности, например «Загрузите ОПиУ за 2024 → +18% достоверности по финансам».

### 2.4 Инкрементальный пересчёт

- **Входы.** На вход приходит `changeSet` — затронутые `metric_key` и периоды из событий. Граф зависимостей «метрика → блоки → итог» строится из библиотеки блоков. Пересчитываются только затронутые блоки, остальные берутся из предыдущего снимка. Итог, риски, quick wins и data_gaps пересчитываются всегда, это дёшево.
- **Склейка событий (debounce).** События по компании собираются в окне 20 секунд через Inngest с ключом `company_id`. Загрузка 10 файлов подряд даёт один пересчёт.
- **Конкурентность.** Одновременно идёт не больше одного пересчёта на компанию: используется уже существующий уникальный индекс `diagnostic_sessions_one_inflight`. Событие, пришедшее во время пересчёта, ставит флаг «нужен ещё один проход».
- **AI-часть отделена от детерминированной.** Балл появляется сразу, а AI-выводы и нарратив догружаются потом. AI перезапускается только для блоков, у которых изменился `input_hash`; механизм `narrative_input_hash` и кэш `analysis-cache.ts` уже есть.
- **Теневой режим при переходе.** Первые 2 недели новый движок работает параллельно со старым `calculatePointA(answers, resolved)`. Разница пишется в `pa_shadow_diffs`, клиенту показывается новый результат. Включение — через флаг `point_a_v4` в реестре настроек.
- **Полный пересчёт** доступен как кнопка эксперта или админа и как ночной cron. Это страховка от дрейфа инкрементального пересчёта.

### 2.5 Снимки, версии, история

- **Каждый пересчёт — строка `diagnostic_sessions`** (`kind = 'point_a'`, `trigger = event | manual | schedule`) и `overview` со снимком.
- **Ссылка на текущую строку `diagnostics`** сохраняется (`is_current` у одной строки, миграция 097).
- **В снимок добавляется:**
  - `config_version` — версия конфигурации блоков;
  - `facts_hash`;
  - `change_reasons[]` — что изменилось относительно прошлого снимка, например: «Финансы +6: маржа 2024 обновлена из документа "ОПиУ_2024.pdf"; расхождение по выручке закрыто клиентом».
- **Хранение:** все снимки за 90 дней. Старше — по одному на неделю. Снимки, проверенные экспертом, хранятся всегда.

## 3. Цели и связь с Точкой Б

- **Единый источник целей** — `metric_targets`. В него добавляются поля `deadline DATE`, `baseline_value`, `baseline_period`, `status`. Цель можно задать по любой метрике каталога.
- **`companies.target_revenue_12m_kzt` / `_3y_kzt`** остаются для совместимости. Они синхронизируются триггером или сервисом с `metric_targets(metric_key = 'revenue', period_label = '12m'/'3y')`. Новый код читает только `metric_targets`.
- **`GoalsBar`** перестаёт хранить пресеты в zustand и сохраняет их в `metric_targets`.
- **Цели из `GrowthSnapshotHero` и цели недели и месяца** перестают дублироваться. Цели периода остаются текстовыми задачами, денежные цели — в `metric_targets`.
- **Блок «Мои цели» в Точке А:**
  - по каждой цели: база (факт Точки А с периодом) → цель → срок, разрыв, требуемый темп (CAGR, MoM);
  - реалистичность: `assessRealism` обобщается со «только выручки» на любую метрику, пороги задаются для каждой метрики в каталоге;
  - статус: on_track / at_risk / behind / no_data;
  - подсказка: «для этой цели не хватает данных: …».
- **Точка Б** (`calculatePointBV2`) берёт базу из снимка Точки А, а цели — из `metric_targets`. Изменение цели (событие `TARGET_CHANGED`) пересчитывает Точку Б и план, а в Точке А — только блок «Мои цели».

## 4. Новая страница Точки А

Маршрут — `/client/point-a`, страница новая. `app/(dashboard)/point-a` → `redirect('/client/point-a')`. Пункт меню (`Header.tsx:63`, `MobileNav.tsx:35`) указывает на новый маршрут. Ленту инсайтов `/point-a/insights` переносим как вкладку или удаляем, если она дублирует риски и выводы.

Структура сверху вниз:

1. **Шапка:**
   - итоговый балл (0–100) и достоверность;
   - стадия и дата последнего обновления;
   - индикатор «пересчитывается…»;
   - кнопки «Обновить данные», «Настроить блоки», «Спросить AI».
2. **Плашка «Требует внимания».** Открытые расхождения с быстрыми кнопками (§5) и топ-3 пункта «Что загрузить». Если ничего нет, плашка не показывается.
3. **Executive Overview.** Главный вывод в 2–3 предложениях, топ-3 риска, топ-3 quick wins, сильные стороны.
4. **Блоки из конструктора.** Карточка блока: балл, достоверность, статус (ок / данных не хватает / гипотеза). Раскрывается в список метрик, у каждой — значение, период, бейдж источника и типа, мини-спарклайн по периодам, сравнение с бенчмарком и AI-вывод по блоку. Клик по метрике открывает её историю и все кандидаты значений.
5. **Мои цели** (§3).
6. **GRI** — отдельная карточка: шкала 0–100 (сейчас GRI на 0–10, отображение переводится в ×10), подпись «GRI — готовность к росту, Точка А — текущее состояние», ссылка на GRI.
7. **Бенчмарки.**
   - Сравнение балла блоков с `lib/point-a/benchmarks.ts` по отрасли и стадии, процентиль.
   - Источник явно подписан: «экспертная оценка, не статистика» — пока `sampleSize = null`.
   - Если подходящего бенчмарка нет, блок не показывается.
8. **История и динамика.** График итога и балла по блокам по снимкам, лента «что изменилось и почему» из `change_reasons`.
9. **Мои данные.** Сводка источников: анкета (процент заполнения), документы (обработано / в работе / ошибка), метрики. Ссылки на редактирование.

Требования:

- **Тексты интерфейса** на русском; тёмная glassmorphism-тема и бренд `#6effc0`.
- **Мобильная версия обязательна:** шрифт в полях ≥ 16px, чтобы iOS не зумил.
- **Скелетоны** при загрузке. Пустое состояние для нового клиента: «Заполните анкету — Точка А построится автоматически».
- **Realtime:** подписка на `diagnostic_sessions` и `data_discrepancies` через `useRealtimeSync`. Страница обновляется сама, без перезагрузки.
- **a11y:** клавиатурная навигация, `aria` у бейджей, контраст AA.
- **Блок «Рынок» в этой версии отсутствует.**

Удаляется после переключения:

## 5. Расхождения: UX

## 6. Единый AI-чат (один мозг)

### 6.1 Архитектура

- **Сервер.** Один эндпоинт `POST /api/v1/ai/chat` со стримингом (SSE). Внутри — `chatWithTools` (`lib/ai/tools-chat.ts`, через OpenRouter и AI gateway проекта).
- **Объединение.** `/assistant/converse` и report-chat переводятся на этот эндпоинт. Старые маршруты оставляются как прокси на один релиз, потом удаляются.
- **История** хранится в `ai_conversations` / `ai_messages` (миграция 053). Нить разговора одна на пользователя и страницу, при этом доступна общая история.
- **Контекст страницы.** Передаётся `surface` (`point_a | gri | point_b | dashboard | …`) и `focus` (`block_key` / `metric_key`). Кнопка «Спросить AI» у блока или метрики открывает чат уже с этим фокусом.
- **UI.** Компонент `components/ai-chat/ChatPanel.tsx`: боковая панель на десктопе, bottom-sheet на мобильном. Встраивается в Точку А, GRI, Точку Б и дашборд. «Гри» открывает ту же панель.

### 6.2 Инструменты

Чтение:

- `get_point_a_snapshot`, `get_point_a_history`, `explain_score(block_key)`;
- `get_facts(metric_key, periods)`, `list_discrepancies`, `get_targets`, `get_gri`, `get_point_b`;
- `search_documents(query)` — RAG, `retrieveUserChunks`.

Запись, **только через подтверждение**:

- `propose_fact_update(metric_key, period, value, reason)`;
- `propose_resolve_discrepancy(id, choice)`;
- `propose_target(metric_key, value, deadline)`.

Как работает запись:

- Инструмент записи ничего не пишет сам. Он возвращает карточку предложения «было → станет» с кнопками «Применить» / «Отмена».
- «Применить» вызывает отдельный эндпоинт `POST /api/v1/ai/actions/{id}/apply` с проверкой сессии и прав. Применение пишется в аудит (actor = пользователь, via = ai_chat) и запускает пересчёт.
- Предложения хранятся в `ai_pending_actions` со сроком жизни 24 часа.

### 6.3 Ограничения

- **Лимиты:** не больше 30 сообщений в час на пользователя, ограничение по токенам на ответ, таймаут на вызов модели.
- **Изоляция данных.** Чат видит только данные текущего пользователя. Эксперт — данные своих клиентов, с явным выбором клиента. Идентификатор клиента берётся из сессии, а не из аргументов инструмента.
- **Ответы опираются на данные.** Цифры в ответе — только из результатов инструментов. Если данных нет, модель так и говорит.
- **Защита от prompt injection.** Текст документов передаётся модели как данные, а не как инструкции. Инструменты записи требуют подтверждения человеком.

## 7. Эксперт

- **Клиент видит Точку А сразу после первого расчёта.**
- **В User 360** у эксперта есть вкладка «Точка А»: тот же вид, что у клиента, плюс:
  - комментарии к блоку или метрике — клиент видит их с подписью эксперта;
  - правка фактов (`source_kind = manual`, автор — эксперт);
  - закрытие расхождений;
  - выбор шаблона и весов;
  - кнопка «Отметить как проверенное».
- **«Проверено экспертом».** Фиксируется версия снимка (`report_versions`, миграция 103) с бейджем «Проверено экспертом {имя}, {дата}». После нового пересчёта бейдж меняется на «Проверено ранее, есть изменения».
- **Гипотезы AI.** Эксперт может подтвердить `AI_HYPOTHESIS` — тогда тип меняется на INFERRED с отметкой эксперта — или отклонить.

## 8. Безопасность и данные

- **RLS** на всех новых таблицах. Клиент видит только свою компанию, эксперт — назначенных ему клиентов, админ — всё. Запись через service-role только из серверных обработчиков, где идентичность берётся из сессии.
- **Таблицы-конфиги** `pa_block_library` и `pa_templates`: читать может любой авторизованный пользователь, писать — только админ.
- **Аудит:** любая правка данных, весов и конфигурации и закрытие расхождений.
- **Миграции** нумеруются от следующего свободного номера. Сейчас в ветке последний — 109, перед созданием сверить с `main`. Применяются через `node scripts/apply-migration.js`.

## 10. Тестирование

- **Юнит-тесты:**
  - `normalize` — парсинг чисел и валют, масштабирование, диапазоны;
  - `survey-facts` — каждый ключ из `SURVEY_FACT_MAP`;
  - `reconcile` — тот же или разный период, порог, автозакрытие;
  - resolver — приоритеты;
  - расчёт блоков — нормировка весов, insufficient_data, гипотезы;
  - инкрементальный пересчёт — результат совпадает с полным пересчётом.
- **Golden-тесты:** 5 эталонных компаний (пустая, только анкета, анкета + документы, с конфликтом, отраслевой шаблон). Снимок сравнивается с эталоном.
- **Свойство:** инкрементальный пересчёт после любой последовательности событий даёт тот же результат, что и полный.
- **API:** RLS и IDOR (чужой `company_id`), подтверждение действий чата, лимиты.
- **E2E:** анкета → загрузка документа с другой выручкой за тот же год → плашка расхождения → «Взять из документа» → пересчёт и `change_reason` → правка цели через чат с подтверждением → Точка Б обновилась.
- **Проверка перед мержем:** `npm test && npm run lint && npx tsc --noEmit`, визуальная проверка страницы на десктопе и мобильном.
