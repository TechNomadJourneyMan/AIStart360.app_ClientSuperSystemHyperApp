# Мастер-промпт: Интернет-магазин в версии AIStart360 Journey

## Роль

Ты — ведущий product engineer, архитектор Next.js/Supabase и security reviewer AIStart360. Реализуй не демонстрацию и не визуальный макет, а рабочую Journey-версию уже существующего Store Control Center.

## Исходный контекст

- В проекте уже существует защищённый Store Control Center на `/store`.
- Store читает опубликованные продажи, прайсы и остатки через `loadStoreOverview` и возвращает только данные владельца текущей Supabase-сессии.
- В проекте уже существует визуальный язык Journey: Точка A, путь A → B, allowlisted-модули и строгая `journeyStateSchema`.
- Отдельный аккаунт интернет-магазина уже является владельцем своей компании и своих `store_*` данных.

## Цель

Создай защищённый маршрут `/client/journey/store`, который показывает тот же Интернет-магазин как управленческий Journey:

1. Точка A — только подтверждённые опубликованные факты магазина.
2. Путь — состояние источников, выявленные ограничения и ближайшее проверяемое действие.
3. Точка B — не придумывать; явно оставить владельцу для постановки измеримой цели.
4. Модули — экономика, операционные метрики, контур данных и риски/возможности.
5. Переходы — из `/store` в Journey и обратно без смены аккаунта или компании.

## Неприкосновенные инварианты

- Не создавай новый Auth user, profile, company, tenant или вторую базу.
- Не копируй строки продаж, остатки, прайсы или закупочные данные в Journey persistence.
- Не клади Store-метрики в React Query, localStorage, IndexedDB или другой клиентский кэш.
- Не принимай `user_id`, `company_id`, workspace owner или Store scope из URL/браузера.
- Владелец определяется только через серверно проверенную Supabase-сессию.
- Доступ должен совпадать с Store: approved client, admin, super_admin; expert, owner, pending, blocked и anonymous не получают данные.
- Для MFA-enrolled пользователя требуется валидный step-up cookie, привязанный к `user.id`.
- Ответ и страница — `private, no-store`, server-first, dynamic.
- Не показывай customer PII, банковские реквизиты, исходные строки импорта или секреты.
- `null` и отсутствующие показатели отображай как «нужно подтвердить», а не как ноль.
- Не выводи прогнозы, цели, средний чек, конверсию, оборачиваемость или рекомендации без проверяемого основания.

## Архитектура

1. Создай чистый детерминированный адаптер `StoreOverview → JourneyState`.
2. Валидируй результат через существующую `journeyStateSchema`.
3. Используй только существующие allowlisted widget kinds; предпочтительно:
   - `finance_cashflow`;
   - `domain_metrics`;
   - `domain_process`;
   - `risks_opportunities`.
4. Страница получает `StoreOverview` непосредственно на сервере через текущую сессию и `loadStoreOverview`.
5. UI получает только агрегированный сериализуемый Journey state и не выполняет отдельный fetch.
6. Добавь CTA «Открыть в Journey» на `/store` и «Вернуться в Магазин» в Journey-версии.

## UX-контракт

- Сохранить визуальный язык Journey, но явно пометить экран как read-only live-представление Store.
- В шапке показать компанию, фактический период, источник и версию публикации.
- На desktop — ясная последовательность «Точка A → Путь → Точка B» и сетка модулей.
- На mobile — те же данные в линейном порядке без горизонтального скролла.
- Алерты Store превращать только в проверяемые риски/следующие действия; текст источника сохранять.
- При пустом Store показать честный zero-state и CTA к импорту, не выдумывая данные.
- Все интерактивные элементы доступны с клавиатуры; заголовки, landmarks и статусы имеют понятные accessible labels.

## Проверка

Обязательные тесты:

1. Адаптер проходит `journeyStateSchema`.
2. Контрольные Store-итоги остаются точными: выручка 28 053 253 ₸, себестоимость 17 139 974,46 ₸, валовая прибыль 10 913 278,54 ₸, маржа около 38,9%, скидка 14 029 367 ₸.
3. `null` остаётся unknown и не превращается в `0`.
4. Точка B и прогнозы не создаются автоматически.
5. Алерты и readiness источников корректно переносятся в allowlisted widgets.
6. Страница не использует browser storage/query cache и не принимает tenant IDs.
7. Anonymous, неверная роль, pending client и MFA без step-up не получают Store-данные.
8. UI имеет zero/partial/complete состояния и корректную mobile-разметку.
9. Пройти targeted Vitest, type-check, lint, route audit и `git diff --check`.

## Граница релиза

В этой фазе реализуй live read-only Journey-представление и безопасную навигацию. Не выполняй production deploy, не меняй пароль/аккаунт и не создавай фоновую синхронизацию без отдельного разрешения пользователя.
