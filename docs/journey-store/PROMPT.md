# Мастер-промпт v2: Интернет-магазин внутри канонического AIStart360 Journey

## Главная команда

Реализуй Store Control Center внутри **ранее спроектированного канонического интерфейса AIStart360 Journey**. Нельзя делать ещё один dashboard, отчётную страницу, вертикальный лендинг или набор обычных карточек. Пользователь должен сразу узнавать тот же Journey: полноэкранное AI-first рабочее пространство, общая интерактивная плоскость, диалог и путь из Точки A в Точку B.

Текущий интерфейс `/client/journey/store` со статичной шапкой, тремя горизонтальными карточками и вертикальной сеткой модулей считать неверной реализацией и заменить.

## Роль исполнителя

Ты — ведущий product designer, frontend architect, Next.js/Supabase engineer и security reviewer AIStart360. Работай одновременно как дизайнер информационной архитектуры и инженер production-системы. Не имитируй Journey внешними цветами: переиспользуй его реальные компоненты, взаимодействия и responsive-модель.

## Продуктовая цель

После входа аккаунтом интернет-магазина пользователь открывает `/client/journey/store` и попадает в полноценный Journey своего магазина:

1. AI сообщает, что уже получил подтверждённые опубликованные данные Store.
2. Точка A показывает реальную текущую экономику и операционный масштаб.
3. Путь выделяет один главный проверяемый управленческий приоритет.
4. Точка B остаётся незаданной, пока владелец сам не выберет метрику, значение и срок.
5. Модули дают детальный контекст, но не перебивают основной путь.
6. Диалог позволяет обсуждать факты, поставить Точку B и построить дальнейшую дорожную карту.
7. В любой момент можно вернуться в полный Store Control Center.

## Канонический интерфейс — обязательные признаки

Используй существующий Journey visual system и по возможности его реальные компоненты:

- полноэкранная рабочая область без dashboard-sidebar;
- верхняя компактная панель Journey с названием компании, source badge, состоянием синхронизации и возвратом в Store;
- на desktop — масштабируемая/перемещаемая плоскость Journey;
- Точка A слева, путь A → B по центру, Точка B справа;
- allowlisted-модули на той же плоскости, а не длинной лентой страницы;
- компактный AI ChatDock снизу, раскрываемый для полноценного диалога;
- dock/панель скрытых и свёрнутых модулей;
- keyboard-accessible перемещение/фокус/сворачивание модулей;
- на mobile — существующая нижняя навигация «Диалог / Путь / Модули» и отдельные адаптированные представления;
- анимации Journey с соблюдением `prefers-reduced-motion`.

Запрещено создавать визуально похожие дубликаты `JourneyCanvas`, `ChatDock`, `WidgetModule`, `ModulesPanel` или mobile navigation. Сначала расширь существующие компоненты через явный mode/config contract.

## Точная геометрия desktop

Не нарушай исходную `conversation-first` механику Journey. Пока Точка A уже подтверждена данными Store, но измеримая Точка B ещё не подтверждена, главным слоем остаётся центрированный AI-диалог стадии `goal`: он компактно показывает подтверждённую Точку A, честно сообщает, что Точка B не задана, и задаёт один вопрос о метрике, значении и сроке. Полноценная плоскость становится главным слоем после подтверждения измеримой Точки B; её также можно открыть явным действием, если канонический UX это разрешает.

В готовом состоянии плоскости должны одновременно читаться пять уровней:

1. **Верхняя системная панель, 56–64 px**
   - слева: AIStart360 Journey + компания;
   - рядом: `Store · live` и версия опубликованных данных;
   - справа: актуальность, статус server sync и CTA «В Магазин»;
   - никаких трёх больших metadata-карточек.

2. **Основной маршрут в верхней половине плоскости**
   - Точка A: `x≈80, y≈180, width≈360`;
   - Путь: `x≈535, y≈150, width≈530`;
   - Точка B: `x≈1160, y≈180, width≈360`;
   - соединения и стрелки не пересекают текст и модули;
   - приоритетный alert отображается внутри пути как следующий шаг, а не отдельной конкурирующей карточкой.

3. **Модули во второй строке плоскости**
   - экономика: слева;
   - ассортимент/остатки: левый центр;
   - готовность источников: правый центр;
   - риски/ограничения: справа;
   - максимум четыре развёрнутых модуля;
   - одинаковый ритм, заголовочная высота и безопасные интервалы;
   - длинный контент ограничивается внутри модуля, не ломает плоскость.

4. **ChatDock**
   - в спокойном состоянии закреплён снизу по центру и не закрывает модули;
   - при постановке цели или обсуждении модуля раскрывается поверх фона с ясным focus state;
   - стартовое сообщение кратко перечисляет происхождение данных и задаёт один следующий вопрос;
   - CTA модуля «Обсудить» открывает тот же ChatDock с grounded draft.

5. **Служебные элементы**
   - controls масштаба/fit/reset — в свободной зоне;
   - module dock не перекрывает Точку B и ChatDock;
   - provenance доступен внутри фактов/модулей, но не повторяется шумом в каждом видимом блоке.

## Точная геометрия mobile

- Никакого уменьшенного desktop-canvas и горизонтального скролла.
- Высота shell равна доступному viewport с safe-area.
- Верхняя строка: компания, Store live, кнопка назад.
- Нижние режимы:
  1. **Диалог** — ChatDock и текущий вопрос;
  2. **Путь** — Точка A → следующий шаг → Точка B линейно;
  3. **Модули** — сортируемый список allowlisted-модулей.
- Основные CTA имеют touch target не менее 44 px.
- Клавиатура телефона не должна закрывать composer.

## Данные Точки A

Показывай только опубликованные значения текущего Store owner:

- компания;
- фактический период;
- выручка;
- себестоимость, если известна;
- валовая прибыль, если известна;
- валовая маржа, если известна;
- скидки и их доля, если известны;
- проданные единицы и возвраты, если известны;
- доступный/зарезервированный остаток, если известен;
- количество товаров и складов, если известно;
- readiness продаж, остатков и прайса;
- Store alerts и limitations.

Контрольная публикация должна отображаться точно:

- выручка: `28 053 253 ₸`;
- себестоимость: `17 139 974,46 ₸`;
- валовая прибыль: `10 913 278,54 ₸`;
- валовая маржа: около `38,9%`;
- скидка: `14 029 367 ₸`;
- продано: `1 324` единицы;
- остаток: `62 039` единиц;
- каталог: `1 365` позиций;
- склады: `4`.

## Grounded AI-контракт

AI имеет право использовать только:

- schema-validated Journey state;
- агрегаты `StoreOverview` текущего пользователя;
- подтверждённые пользователем цели и сообщения;
- server-owned provenance и limitations.

AI не имеет права:

- придумывать Точку B, прогноз, средний чек, конверсию, оборачиваемость или причинность;
- выдавать alert за доказанную рекомендацию;
- менять server-owned Store facts;
- подключать внешние источники без реального connector status;
- смешивать данные другого аккаунта/компании.

Первый вопрос при полной Точке A: «Какой показатель магазина вы хотите изменить, до какого значения и к какому сроку?»

После ответа цель остаётся draft/pending до явного подтверждения владельцем. Только подтверждённая измеримая Точка B разрешает строить roadmap.

## Архитектура состояния

1. `StoreOverview → JourneyState` остаётся чистым детерминированным адаптером и проходит `journeyStateSchema`.
2. Store facts имеют стабильные IDs и server-owned статус `confirmed`.
3. Не создавать нового Auth user, profile, company, tenant или базу.
4. Не копировать raw sales/inventory/price rows в Journey.
5. Не хранить Store facts в React Query, `localStorage`, IndexedDB или guest cache.
6. Для signed-in Store Journey использовать отдельный детерминированный server workspace
   `journey-store-user-${user.id}` с database persistence. Он принадлежит тому же
   пользователю, но не может стать canonical workspace обычного Journey и не создаёт
   новый tenant/Auth user/company.
7. Синхронизацию live Store facts выполнять server-side при загрузке/обновлении, сохраняя пользовательские goals, roadmap, сообщения и layout отдельно от server-owned facts.
8. Browser не передаёт `user_id`, `company_id`, owner или Store scope.
9. Любой Store GET/chat/document/patch route повторно проверяет session, Store
   role/status и MFA; middleware недостаточно для `/api/*`. Client header не может
   включить или обойти Store security context: доверие определяется самим server route.
10. При конфликте версий не терять пользовательскую цель или layout; применять существующую revision/conflict модель Journey.

Если полноценное безопасное разделение server-owned Store facts и user-owned Journey state требует расширения persistence schema/merge policy, реализуй это явно и протестируй. Не обходи проблему статичной отдельной страницей.

## Доступ

- Разрешены: approved `client`, `admin`, `super_admin`.
- Запрещены: anonymous, pending/rejected/blocked/archived client, `expert`, `owner`.
- MFA-enrolled пользователь без валидного step-up получает challenge до чтения Store данных.
- Все Store/Journey endpoints: `private, no-store`.
- Tenant определяется только серверной Supabase-сессией.

## Empty/partial/error UX

- Empty: канонический Journey shell остаётся, Точка A честно сообщает об отсутствии публикаций, в пути один CTA «Импортировать данные».
- Partial: известные метрики отображаются, отсутствующие — `Нужно уточнить`; нули не подставляются.
- Error: ранее загруженные финансовые данные скрываются, если server access не подтверждён; показывается безопасное восстановление.
- Никогда не переключаться на публичный HONOR demo или guest local fallback для этого маршрута.

## Acceptance tests

Обязательны:

1. Canonical Journey visual shell присутствует: canvas, ChatDock, Point A, roadmap, Point B, widget modules, mobile navigation.
2. Старый отдельный `StoreJourneyView`/вертикальный dashboard больше не используется маршрутом.
3. Точные контрольные итоги сохраняются без float/format drift.
4. `null` остаётся unknown, а не `0`.
5. Точка B отсутствует до явного подтверждения; roadmap не выдумывается.
6. Store facts нельзя отредактировать/reject через клиентский UI.
7. Пользовательские goal/layout/messages переживают refresh; live Store facts обновляются из источника.
8. Никаких Store facts в `localStorage` или React Query cache.
9. Anonymous/pending/expert/owner/MFA-no-step-up не получают данные.
10. При `?from=/client/journey/store` approved client/admin/super_admin возвращаются на нужный маршрут.
11. Desktop 1440×900: до Точки B виден канонический центрированный dialog stage `goal`; после подтверждения цели основной путь и четыре модуля видны без перекрытия ChatDock/module dock.
12. Mobile 390×844: работают три режима, нет горизонтального скролла и composer не закрыт навигацией.
13. Keyboard/reduced-motion/accessibility проверки проходят.
14. Targeted tests, полный Vitest, type-check, lint, route audit и production build проходят.
15. После deploy выполнить authenticated production smoke: компания и контрольные метрики видны, диалог открывается, чужие данные отсутствуют.

## Definition of Done

Задача завершена только когда:

- интерфейс визуально и интерактивно является каноническим Journey;
- Store встроен в него как доверенный live-контекст;
- сохранены security/tenant boundaries;
- desktop и mobile acceptance выполнены;
- новый production deployment имеет статус `READY`;
- `aistart360-store.vercel.app/client/journey/store` указывает на исправленную версию;
- документация честно фиксирует выполненные и невыполненные проверки.
