### Upgrade-экран

Единый компонент `components/paywall/UpgradeSheet.tsx`: что заблокировано, что даёт тариф
(3 пункта, релевантные фиче), цена, CTA → checkout (сейчас stub-флоу — он уже публичный и
рабочий как демо). Тон — без давления: «Это возможность Pro. Ваши текущие данные и отчёты
останутся доступны бесплатно всегда».

### События и включение

`paywall_events` (миграция 054): user_id, feature, event(`view|hit_limit|upgrade_click|upgraded`),
tier, created_at → метрики paywall view→upgrade. Включение фичегейтов — конфиг
`lib/paywall/limits.ts` + kill-switch env `PAYWALL_ENFORCE=false` (до эквайринга: события
собираются, лимиты **не** применяются — «тихий режим» для калибровки).

### Тесты

1. `PAYWALL_ENFORCE=false` → ничего не блокируется, события пишутся.
2. Лимит чата достигнут → UpgradeSheet, диагностика работает (тест 26).
3. Смена tier мгновенно меняет entitlement (без кэш-залипания >5 мин).
4. Отказоустойчивость: Upstash недоступен → fail-open (не блокировать пользователей из-за инфраструктуры).

## G2. GRI-кредиты для агентств (L3 · M · 🔥)

- **Модель:** кредит = 1 полная диагностика клиента агентства. Не сгорают (продукт-обещание).
- **Схема (отдельная миграция при старте):** `gri_credit_accounts` (id, org_id, balance int,
  created_at) + `gri_credit_transactions` (id, account_id, delta int, kind
  `purchase|spend|refund|adjust`, actor_id, client_ref, note, created_at; баланс — только
  через транзакции, CHECK delta≠0; инвариант: balance = Σdelta, пересчёт-проба).
- **API:** `POST /api/v1/agency/credits/spend` (создаёт клиентскую диагностику, списывает 1,
  атомарно в одной транзакции), `GET /api/v1/agency/credits` (баланс+история). Покупка — через
  checkout (после эквайринга); до того — ручное начисление админом (giga-panel, kind='adjust',
  audit_log).
- **Ownership:** отчёт принадлежит агентству; клиент агентства получает share-ссылку
  (существующий механизм). Персональные данные клиента — ответственность агентства (фикс в оферте).
- **UX:** агентский кабинет = существующий owner-кабинет + блок кредитов; admin UX — giga-panel
  модуль (баланс, начисление, история).
- Тесты: атомарность списания (конкурентные spend), баланс не уходит в минус, audit на adjust.

## G3. White-label «GRI для консультантов» (L3 · L · 🔥🔥)

**Концепт:** консультант/бухгалтер/коуч ведёт клиентов через GRI под своим брендом; AIStart360 —
движок. **MVP-scope (когда дойдёт):** поддомен `{partner}.aistart360.app`, логотип+цвет партнёра
(тема уже CSS-переменными), партнёрский дашборд = агентский кабинет (G2), отчёты с двойным
футером «Powered by AIStart360». **Не в MVP:** кастомные домены, кастомизация методологии,
API-доступ.

**Архитектурные последствия:** таблица `partners` (slug, branding jsonb, owner_org_id);
middleware-резолв поддомена → theme-контекст; данные клиентов скоупятся org_id (модель уже есть
в Prisma `Organization`). **Onboarding партнёра:** ручной (админ создаёт), договор о данных
обязателен. **Риски:** (1) конфликт ownership данных клиентов — решить в договоре ДО кода;
(2) репутационный — партнёр продаёт под нашим движком некачественно → модерация партнёров;
(3) поддержка второй «арендаторской» оси в RLS — самая дорогая часть, требует отдельного
security-ревью. **Rollout:** 1 пилотный партнёр вручную → шаблонизация. Приоритет L3 подтверждён:
не начинать до устойчивой монетизации ядра.

## G4. Mini-GRI лиды → в мини-CRM (M2 · S поверх Фазы 2 CRM · 🔥🔥) `[DEP: GRI/CRM]`

Существующее: `mini_gri_leads` (score, block_scores, converted); раздел «Лиды» в giga-panel
(параллельная ветка). Достроить:

- **Поток:** insert в `mini_gri_leads` → (тот же обработчик) upsert в `crm_clients` владельца
  портала: имя=email-префикс, source='mini-gri', сегмент по зоне (`red|amber|green` из
  `zoneForScore`), заметка «Mini-GRI {score}/100, слабый блок: {block}» + рекомендованный
  follow-up (`crm_reminders`: red → «позвонить в 24ч», amber → «письмо с разбором», green →
  «предложить полную диагностику»).
- **Согласие (тест 27):** в форму email mini-GRI добавить чекбокс «Согласен получить разбор
  результатов» (unchecked по умолчанию для звонков; сам email-результат — legitimate interest,
  фиксируем текстом). Без галочки — лид попадает в CRM с пометкой `no_contact_consent`
  (нельзя звонить, можно считать в статистике) — правило отображается в CRM-карточке.
- **NBA-интеграция:** свежие red-лиды портала-владельца попадают в сигнал S1 (для owner-роли портала).
- Тесты: дедуп по email, сегментация по зоне, consent-флаг блокирует напоминание «позвонить»,
  converted=true при регистрации лида.
