# Пакет III — Retention

## C1. Weekly-дайджест «1 инсайт + 1 действие» (M2 · S поверх Фазы 4 · 🔥🔥)

`[DEP: GRI/CRM]` — cron уже есть (vercel.json 09:00 Алматы → колокольчик); Фаза 4 добавит
Email/Telegram-доставку. Здесь специфицируется **генератор контента** `lib/digest/weekly.ts`.

### Шаблон дайджеста

```
Тема: {Имя}, ваш бизнес за неделю: 1 инсайт и 1 действие
1) Инсайт недели: {insight}                    ← из Гри-инсайтов / изменения пульса / метрик
2) Главное действие: {NBA.title} — {reason}    ← ре-юз A2 (тот же selectNextBestAction)
3) Слабый блок GRI недели: {блок} {score}/10   ← min(section_avgs) или падение пульса
4) Кому позвонить: {top-3 из crm_reminders}    ← [DEP]
5) Просрочено: {n напоминаний, m задач плана}
6) Что изменилось: {пульс Δ, прогресс плана Δ%}
CTA: [Открыть дашборд] [Спросить ГРИ]
```

### Логика генерации и персонализация

- Детерминированная сборка секций (нет данных → секция пропускается; минимум для отправки:
  ≥2 содержательные секции, иначе неделя пропускается — не шлём пустышки).
- `insight` — единственная LLM-часть (Haiku, тот же путь, что `buildScreenInsight`, с
  `can_generate=false`-фолбэком → тогда инсайт = детерминированное «изменение недели»).
- Тон — выбранная персона ГРИ (файл 06) влияет только на 1 вводную фразу, не на данные.

### Доставка, privacy, unsubscribe

- Каналы: колокольчик (есть), email (Resend), Telegram (Фаза 4 bot-binding). Отправка **только
  при consent** `weekly_digest` (файл 12; дефолт: in-app on, email/tg off до явного включения).
- Unsubscribe-ссылка в каждом письме → `user_consents.weekly_digest=false` (одним кликом,
  без логина — подписанный токен).
- Тест 28: дайджест не отправляется без согласия (обяз. тест).

### Тесты

1. Пользователь без CRM/плана получает дайджест из доступных секций (или пропуск).
2. NBA в дайджесте == NBA на дашборде в момент генерации (единый селектор).
3. Отписка → следующая генерация пропускает канал. 4. LLM-fail → детерминированный инсайт.

## C2. Re-scan через 90 дней + празднование роста (M2 · S-M · 🔥🔥)

- **Reminder:** сигнал S7 в NBA (есть) + запись в `app_notifications` на 90-й день
  (cron `[DEP]`); email — после Фазы 4 с тем же consent.
- **Milestone-экран:** после сохранения нового assessment сравнить с предыдущим
  (`gri_assessments` история есть): Δ≥+0.3 → полноэкранный milestone
  «GRI вырос: 3.2 → 5.7» + радар before/after (два слоя `GRIAssessmentRadarWidget`) +
  анимация радующегося маскота (поза `insight` + конфетти, framer-motion) + share-card (D4) +
  «Что дальше: обновим план 90 дней?» → регенерация плана (A4 §5).
- Δ<0 → **без стыда**: «Индекс снизился на 0.4. Это нормально после честного пересмотра ответов.
  Смотрим, что изменилось →» (diff-список блоков).
- **Celebration copy:** короткое, конкретное, без «вы лучший»: «+2.5 за 90 дней. Сильнее всего
  выросли Продажи (+3.1). Так держать 🐾».
- **Данные:** ничего нового — история уже в `gri_assessments`; событие `rescan_milestone` в
  `assistant_events`.
- Тесты: пара assessment'ов → корректный Δ и экран; один assessment → экран не показывается;
  повторный просмотр — из истории, без дублей событий.

## C3. Стрик пульса (L3/M2 · S · 🔥)

- **Расчёт на лету** из `gri_pulse_responses.week_start` (стрик = число подряд идущих недель
  до текущей; ничего не храним — воспроизводимо и без миграций).
- UI: маленький огонёк у виджета пульса «3 недели подряд» + реплика маскота на 4/8/12 неделях.
- **Правила:** пропуск одной недели сбрасывает; «пауза» — если в неделе есть заявленный отпуск
  (MVP: нет пауз, просто мягкий сброс). **No-shame:** при сбросе никакого «вы потеряли…» —
  «Начнём новую серию на этой неделе?».
- **Анти-dark-pattern:** без push-спама (максимум 1 nudge в неделю в колокольчик), без монетизации
  стрика, без публичного шейминга, отключаемо в настройках ассистента.
- Тесты: границы недель (UTC-понедельник — существующий `mondayOfWeekUTC`), сброс, cap-отображение.

## D2. Якорь vs консалтинг + ROI-калькулятор (M2 · S · 🔥🔥)

- **Блок сравнения (честный):** «Стратегическая сессия с консультантом — обычно $5–25K и 4–6
  недель. AIStart360 — диагностика за вечер и план на 90 дней. Это не замена консультанту —
  это способ прийти к нему (или к решению) подготовленным». Без принижения конкурентов.
- **Калькулятор «стоимость хаоса»** (client-компонент, без бэкенда): входы — выручка/мес,
  средний чек, лидов/мес, % потерянных лидов (слайдер), часы собственника в операционке.
  Формула: `потери = лиды × %потерь × чек × 0.35 (консервативный коэф. закрытия) + часы × ставка`.
  Вывод — **диапазон** (±40%): «Хаос может стоить вам ≈ 0.8–1.9 млн ₸ в месяц».
- **Assumptions и дисклеймер обязательны:** «Оценка по вашим вводным и усреднённым коэффициентам;
  не является финансовым расчётом» + раскрываемый список допущений.
- Тесты: формула-юниты, крайние значения (0 лидов), диапазон всегда показывается диапазоном.

## D3. Self-serve активация (H1 · S-M · 🔥🔥🔥)

### Аудит текущего гейта (чек-лист выполнен)

Регистрация → `profiles.status='pending_approval'` + `admin_requests`; ждёт ручного approve;
решение унифицировано в `applyApprovalDecision()` (`lib/users/approval.ts:46`); режимы
`open|approval|invite` уже есть (`040_system_settings.sql`, `app/api/giga-admin/settings/registration`).

### Новая логика: режим `auto`

```
register → computeRiskFlags(candidate) → riskScore
  ├─ score < THRESHOLD_AUTO (напр. 30)  → applyApprovalDecision('approved', actor:'system:auto')
  │                                        + AuditLog(auto_approved, flags)
  ├─ score ≥ THRESHOLD_AUTO             → status pending_approval + admin_requests
  │                                        (payload.risk_flags[]) — ручная модерация как сейчас
  └─ всегда: email-verification обязателен ДО auto-approve (Supabase confirm)
```

### Risk-флаги `lib/registration/risk.ts` (каждый — вес)

одноразовый/disposable email-домен (+25); ≥3 регистрации с одного IP за 24ч (+30, Upstash-счётчик);
неподтверждённый email (блокирует auto, не скорит); имя/компания из стоп-словаря спама (+20);
запрещённые тематики в поле «о компании» (словарь, +40); user-agent/скоростные аномалии формы —
заполнение <5 сек (+15); повторная регистрация ранее rejected email (+40). Плюс admin override:
ручная блокировка/одобрение всегда сильнее (`applyApprovalDecision` уже пишет actor).

### Изменения

`lib/settings/system-settings.ts` (+'auto'), `app/api/auth/register/route.ts` (ветка auto),
`lib/users/approval.ts` (actor='system:auto', причины), admin UI: фильтр «авто-одобренные»,
кнопка «отозвать доступ» (существующий reject-путь). Миграция 051 — только если понадобится
колонка (риск-флаги влезают в `admin_requests.payload`).

### Rollout и тесты

Rollout: `auto` включается giga-переключателем (по умолчанию остаётся `approval`) → неделя
наблюдения (метрика: доля флагов, abuse-инциденты) → дефолт. Rollback = переключить режим назад
(мгновенно). Тесты (обяз. 21, 22): чистый пользователь проходит без ручного шага; disposable-email
/ 3 регистрации с IP → pending + флаги в payload; audit-записи на каждое авто-решение.

## F1. Conversational intake pilot (H1/M2 · M · 🔥🔥)

- **Какой блок:** **Step 9 «Финансы» (`s9n_*`)** — самый болезненный (числа, стыд, бросают),
  самый ценный (питает Point A/B/trust) и уже имеет alias-инфраструктуру. `ASSUMPTION:` метрика
  drop-off по шагам не собирается — добавить событlong `survey_step_view/complete` до пилота,
  чтобы был бейзлайн.
- **Flow:** на входе в шаг — выбор: «Заполнить формой» / «Рассказать ГРИ» (A/B: 50/50 среди
  новых; вернуться к форме можно всегда, ответы переносятся). Диалог: ГРИ спрашивает по одному
  полю («Какая выручка была за 2024? Примерно — тоже ок»), парсит свободный ответ →
  подтверждение чипом («Записал: 42 млн ₸/год. Верно?») → пишет в те же `survey_answers`
  (`s9n_*`) через существующий upsert. Поле «не знаю/пропустить» — легально.
- **Валидация:** существующий `runValidation` L1/L2 на лету (диапазоны, согласованность
  маржа/выручка); LLM-парсер числа/валюты (Haiku, structured `{field,value,unit,confidence}`,
  confidence<0.7 → переспросить).
- **Fallback:** любой сбой LLM → «давайте формой» с сохранённым прогрессом.
- **Метрики пилота:** completion шага, time-to-complete, доля `null`-полей, качество
  (post-hoc: доля значений, изменённых пользователем позже), эскалации.
- Тесты (обяз. 24): диалог сохраняет структурированные `s9n_*`; переключение диалог↔форма без
  потери; инъекция в свободном ответе не исполняется.

  `{verdicts: [{claim, verdict: confirmed|disputed|cannot_verify, note}]}`.

  моделью. Это снижает, но не исключает вероятность ошибки».

  (проверка асинхронная, бейдж догоняет).
