# Сторож и сигналы: как платформа сообщает о своих сбоях

Здесь описано, как портал и сервис агентов узнают, что плановые задачи остановились, а платформа или база легли, и как об этом узнают люди. Раунд 4, пакет R4-A1: закрывает находки N4A-2…N4A-5, N4A-7, N4A-14, N4A-15 и R-061 аудита `docs/audit-2026-11/R4-AUDIT-A.md`. Бэкапы и их сторож описаны отдельно в [docs/backup/README.md](../backup/README.md).

| Что | Где |
|---|---|
| Журнал исходов задач | таблица `public.ops_job_runs`, миграция `supabase/migrations/154_ops_job_runs.sql` (откат — `rollback/154_ops_job_runs.down.sql`) |
| Запись в журнал | `lib/ops/job-journal.ts`: свой пул `pg` на одно соединение к той же базе, что у Prisma этого процесса (`DATABASE_URL`; `DIRECT_URL` при `PRISMA_DATASOURCE=direct`) |
| Планировщик: исход каждого вызова, неудачные захваты | `lib/cron/runner.ts`, подключение — `lib/runtime/server-start.ts` |
| Функции Inngest: исход запусков по расписанию, пинг | `lib/functions/ops-ping.ts`, подключение — `lib/functions/registry.ts` |
| Сторож задач | `lib/ops/job-watchdog.ts`, `GET /api/cron/ops-watchdog` раз в 10 минут (в :03, :13, … UTC) |
| Перекрёстный сторож | `lib/ops/crosswatch.ts`, `GET /api/cron/ops-crosswatch` на сервисе агентов раз в 3 минуты |
| Тревога без базы | `lib/notifications/ops-direct.ts` |
| Готовность для внешней проверки | `GET /api/health` (`lib/health/platform.ts`); `GET /api/healthz` — только «процесс жив» (проверка деплоя Railway) |
| ГИГА | Настройки → «Состояние системы» → «Задачи по расписанию и тревоги» |
| Чистка истории Inngest | `scripts/ops/inngest-history-prune.sql` (запуск вручную, см. §6) |

## 1. Как это работает

```
Планировщик портала и сервиса агентов (lib/cron/runner.ts), каждую минуту
 ├─ захват минуты в workflow-db (cron_runs; не ответил за 15 с = неудача) ── не удаётся 5 мин подряд ──► console.error
 │                                                                       + тревога без базы (Telegram)
 │                                                                       повтор раз в 6 ч, «снова работает»
 ├─ вызов маршрута → исход в ops_job_runs: ok / http_error / error / timeout / claim_failed
 │
Сервер Inngest (наш, Railway) → POST /api/inngest
 ├─ каждая функция с cron: конец запуска → ops_job_runs (ok / error последней попытки)
 └─ ops-ping каждые 10 мин → своя строка в ops_job_runs (цепочка «Inngest → портал → база»)

Портал: /api/cron/ops-watchdog раз в 10 минут
   задача давно не запускалась (интервал × 2, не меньше интервала + 15 мин)
                                   → CRITICAL для частых задач (≤ 15 мин), иначе WARNING
   задачи нет в журнале вовсе      → то же, когда её ждут дольше допустимого срока (с первого
                                     прохода, в котором она появилась в расписании, —
                                     ops_job_expectations; новая задача в новом выпуске — не тревога)
   последний запуск редкой / три последних частой — с ошибкой → WARNING
   очередь пересчёта Точки А: только строки, чей срок прошёл > 1 ч назад и которые никто не
     разбирает → WARNING, > 6 ч → CRITICAL (глубина ночной волны — не тревога: её законно
     кладут в очередь на ближайший час, и крон агентов разбирает её каждую минуту)
   проверки мониторинга без ИИ (очередь агентов старше 15 мин, зависшие и dead-задачи, документы,
     одобрения, CRM, расход ИИ) — всегда, независимо от «Агентов 24/7»
   демо-аккаунтов за сутки > 20, или есть старше 48 ч (очистка не идёт) → WARNING
   сервис агентов не отвечает на /api/healthz два прохода подряд (портал с PORTAL_ROLE=web) → CRITICAL
   ни один Super Admin (тревоги сторожа уходят только им) не привязал Telegram, и нет
     TELEGRAM_ADMIN_CHAT_IDS с токеном бота → WARNING «Тревогам некуда приходить» (раз в сутки)
   → notifyStaff: лента ГИГА + Telegram Super Admin + старые чаты TELEGRAM_ADMIN_CHAT_IDS + письмо (CRITICAL)
     об одной проблеме — не чаще раза в 6 ч
   ретенция: строки ops_job_runs старше 30 дней, кроме последнего исхода каждой задачи (месячная
     задача с допуском 62 дня не теряет свой последний запуск), и cron_runs старше 30 дней
     (до 20 000 за проход)
   база не читается два прохода подряд → тревога без базы
   сбой отправки одной тревоги не обрывает проход: остальные тревоги и чистка идут; но проход
     отвечает 502 «alerts_not_delivered» (в журнале — ошибка), шлёт тревогу без базы, и ГИГА
     показывает «Тревоги не доставлены»

Сервис агентов: /api/cron/ops-crosswatch раз в 3 минуты
   GET {портал}/api/health (10 с) и своя связь с базой (SELECT 1, 5 с)
   две неудачи подряд → тревога без базы; повтор не чаще раза в 6 ч; «восстановлено»
   «не отвечает» и «не готов» — одна серия; «восстановлено» — только после ответа 200
```

**Тревога без базы** уходит одним вызовом Bot API на каждый чат из `TELEGRAM_ADMIN_CHAT_IDS`: админ-ботом (`TELEGRAM_ADMIN_BOT_TOKEN`), а без его токена — клиентским (`TELEGRAM_BOT_TOKEN`). Таймаут 8 с на запрос. Если чатов нет, ничего не отправляется: один раз за жизнь процесса в лог пишется `ops: TELEGRAM_ADMIN_CHAT_IDS не задан …`.

## 2. `/api/health` и `/api/healthz`

- `/api/healthz` — для Railway. Отвечает «процесс жив»: ни базы, ни сети. Не менять.
- `/api/health` — готовность, публично и без подробностей: только `ok`/`fail`/`unknown` по проверкам, без имён переменных, задач и адресов. Код 503, если провалена любая проверка:

| Проверка | Когда есть | Провал |
|---|---|---|
| `db` | всегда | `SELECT 1` упал или не ответил за 3 с (медленный ответ ≥ 400 мс — «degraded», не провал) |
| `config` | всегда | не хватает критичных переменных или переменных связки сервисов (R-061, по числу) |
| `queue` | портал на Railway | очередь Workflow не запущена |
| `inngest` | портал с `INNGEST_SELF_HOSTED_URL` | последний успешный `ops-ping` старше 30 мин; пинга нет вовсе, а сторож ждёт его дольше 30 мин |
| `jobs` | процесс с `CRON_RUNNER_ENABLED=1` | планировщик этой роли ничего не вызывал 15 мин (при строках этой роли старше 15 мин; если строк роли нет вовсе — когда процесс работает дольше 15 мин) |

Нет данных (журнал только что создан, миграция 154 не применена) — `unknown`: это «degraded», не провал. Результат кешируется на 15 с, поэтому частые проверки не нагружают базу.

**Переменные связки сервисов (R-061)** проверяются при старте процесса, одной строкой `server: не заданы переменные связки сервисов …` в логе ошибок, и считаются в `config`:

- `CRON_SECRET` — если работает планировщик или роль задана;
- секрет внутренних токенов — `INTERNAL_TOKEN_SECRET` (или `AUTH_SECRET` / `NEXTAUTH_SECRET` / `GIGA_COOKIE_SECRET`);
- `AGENTS_SERVICE_URL` — у портала с `PORTAL_ROLE=web`;
- `INNGEST_SELF_EVENT_KEY`, `INNGEST_SELF_SIGNING_KEY` — если задан `INNGEST_SELF_HOSTED_URL` (не у сервиса агентов).

## 3. Переменные

| Переменная | Сервис | Зачем |
|---|---|---|
| `TELEGRAM_ADMIN_CHAT_IDS` | портал и агенты | Чаты для тревог без базы, через запятую. **На проде не задана** (2026-11-16). Без неё тревоги без базы есть только в логах |
| `PORTAL_SERVICE_URL` | агенты | Адрес портала в частной сети, например `http://<портал>.railway.internal:8080`. Без неё перекрёстный сторож проверяет публичный `NEXT_PUBLIC_APP_URL` |
| `TELEGRAM_ADMIN_BOT_TOKEN` | портал и агенты | Уже есть; им отправляется тревога без базы |

Чтобы узнать id чата: написать админ-боту, затем `getUpdates` или переслать сообщение `@userinfobot`. Группа — отрицательный id.

## 4. Выкатка

1. Бэкап, затем миграция 154 (через `db-tools`, как остальные). Без неё код работает: запись журнала пропускается с одной строкой в логе, сторож отвечает `journal: not_migrated`, `/api/health` пишет `unknown`.
2. Код на портал и сервис агентов.
3. `PUT /api/inngest` — без синхронизации сервер Inngest не знает про `ops-ping`; через 30 минут `/api/health` портала ответит 503 (`inngest: fail`), а сторож поднимет «пинг Inngest ни разу не запускался».
4. Проверить: через 10–15 минут ГИГА → «Состояние системы» показывает задачи с «норма»; в журнале есть строки от `web` и `agents`.
5. По желанию: `TELEGRAM_ADMIN_CHAT_IDS` (портал и агенты), `PORTAL_SERVICE_URL` (агенты), привязка Telegram сотрудников в ГИГА → «Уведомления».

**Откат.** Код — предыдущий деплой. Миграция — `rollback/154_ops_job_runs.down.sql`; старый код таблицу не читает, новый без неё работает (см. п. 1).

**Первые дни.** Возможны ложные «давно не запускалась» для задач, которые на проде выключены или падают по известной причине. Повтор — не чаще раза в 6 ч на проблему. Проверить по ГИГА и решить: поправить задачу или её расписание.

## 5. Если пришла тревога

| Тревога | Где смотреть |
|---|---|
| «Задачи по расписанию не запускаются» (захват в workflow-db) | Сервис `workflow-db` в Railway; переменная `WORKFLOW_POSTGRES_URL` у портала и агентов. Пока она лежит, не выполняется ни одна задача по расписанию, в том числе сторожа |
| «Портал не отвечает» / «Портал отвечает, но не готов» | Деплой и логи портала; `/api/health` — какая проверка провалена |
| «База данных не отвечает сервису агентов» | Postgres в Railway; скорее всего, портал тоже не работает |
| «Задача … давно не запускалась», `inngest:*` | Сервис `inngest` в Railway, затем `PUT /api/inngest` |
| «Задача … давно не запускалась», `/api/cron/*` | Логи планировщика сервиса (`cron: GET …`), `CRON_RUNNER_ENABLED`, `CRON_SECRET` |
| «Очередь пересчёта Точки А не разбирается» | Сервис агентов (`/api/cron/agents`) и функция `point-a-recalc` |

## 6. Чистка истории Inngest

Сервер `inngest/inngest:v1.52.0` не удаляет старую историю сам: у `inngest start` нет флагов ретенции. База `inngest` на Postgres-sfat 16.11 весила 33 MB при ~350 запусках в сутки — рост медленный, но бесконечный.

`scripts/ops/inngest-history-prune.sql` удаляет историю старше N дней (по умолчанию 30).

**Что известно о схеме.** Схемы сервера Inngest в репозитории нет. Подтверждено запросами к проду только `function_runs (run_id, run_started_at, function_id)` и `function_finishes (run_id, status, output)`. Поэтому:

- по умолчанию удаляются только **завершённые** запуски старше срока: строки `function_finishes` и `function_runs`. Идущий или зависший запуск не трогается;
- неподтверждённые таблицы (`history.created_at`, `events.received_at`, `traces.timestamp`, `spans.start_time`) скрипт проверяет по `information_schema`. Удаляет он их только с `-v include_unconfirmed=1` и только если колонка — `timestamp`/`timestamptz`; иначе пишет «пропущено» с причиной;
- `apps` и `functions` (регистрация приложений) не трогаются никогда;
- база не `inngest` и срок меньше 7 дней — отказ.

**Порядок (решает оркестратор / PO):**

1. Пробный прогон по частной сети через `db-tools`: `psql "$INNGEST_DB_URL" -X -v ON_ERROR_STOP=1 -f scripts/ops/inngest-history-prune.sql`. Он печатает опись (таблицы, размер, строки) и сколько строк попало бы под удаление; транзакция откатывается.
2. По описи решить, какие таблицы реально растут. Если основной объём в неподтверждённых — сначала сверить их схему (`\d history` и т. п.) с ожиданиями скрипта.
3. Удаление: тот же вызов с `-v apply=1` (и, при необходимости, `-v include_unconfirmed=1`). Удаление идёт одной транзакцией, `lock_timeout` 5 с, `statement_timeout` 5 мин. Лучше днём, не в 22:00–23:00 UTC и не в 03:00–06:00 UTC.
4. По желанию — `VACUUM (ANALYZE)` отдельно. Не `VACUUM FULL`: он блокирует таблицы сервера Inngest.
5. Регулярный запуск (например, раз в неделю cron-сервисом или вручную) пока **не настроен**: решение за оркестратором после первого прогона.

Тест скрипта на модели подтверждённых таблиц — `tests/integration/db/inngest-history-prune.test.ts` (отдельная временная база на локальном тестовом сервере).
